## Goal

Инвариант «import(export(БД)) == БД», запиненный в state-git-import РАЗОВЫМ замером на живой БД, с тех пор регрессировал и никто не заметил: стоячего гейта нет. Сегодня на живом дереве dry-run импорт репортит 336 updated + 437 journal, то есть `tausik sync` — команда, которую инженер запускает после git pull — НЕ идемпотентна, а РАЗРУШИТЕЛЬНА.

Четыре независимые асимметрии + один маскирующий дефект:
D1 (маскирующий) sync_suggested не укладывается в 6-секундный watchdog на ХОЛОДНОМ первом вызове session_open — а /start делает ровно один вызов. Секция деградирует КАЖДУЮ сессию, поэтому D2-D5 невидимы уже 5 сессий. На тёплом вызове та же секция отвечает за 0.33s — то есть работа дешёвая, дорог холодный старт (импорт state_import/state_parse + первое чтение 2024 файлов).
D2 (порча данных) parse_journal._JOURNAL_RE построчный: `^- <ts> [phase] — <msg>$`. Экспортёр же пишет МНОГОСТРОЧНЫЕ сообщения (структурированная AC-evidence из task_done попадает в task_logs с \n). При реимпорте выживает только первая строка → ключ мультимножества (created_at,message,phase) не совпадает с БД → 437 строк выглядят «отсутствующими» → реальный sync ДОПИШЕТ 437 обрезанных дублей журнала. Именно эта фича (многострочная AC-evidence) появилась ПОСЛЕ пина state-git-import и сломала его инвариант.
D3 (шум) memory.tags: экспорт сортирует, БД хранит порядок вставки → 239 фантомных updated; sync переписал бы 239 строк ради переупорядочивания.
D4 (шум) tasks.completed_at: БД '2026-03-14T15:23:42+00:00', файл '2026-03-14T15:23:42Z' — один и тот же момент, разная сериализация → 94 фантомных updated.
D5 (тихая потеря) поле, отсутствующее в файле, сравнивается как None и попадает в changed → UPDATE ... SET relevant_files=NULL. Политика «файлы побеждают» задумана для РАСХОЖДЕНИЯ значений, а не для ОТСУТСТВИЯ поля; сейчас устаревшая проекция молча откатывает БД.

Задача: починить все пять, а инвариант перевести из разового замера в СТОЯЧИЙ гейт, чтобы следующая фича не сломала его снова незамеченной.

## Acceptance Criteria

ПРИНЦИП ФИКСА (общий для 1-4): проекция — канонизирующее лоссовое представление (flatten_line для журнала, sorted для tags, normalize_ts для времени). Детектор расхождений обязан сравнивать в КАНОНИЧЕСКОМ пространстве, прогоняя обе стороны через те же нормализаторы эмиттера, а не сырую БД против канонизированного файла. Эмиттер НЕ трогаем.

1. D2 ЖУРНАЛ ИДЕМПОТЕНТЕН: мультимножество журнала ключуется на канонизированной форме — flatten_line(message) и normalize_ts(created_at) применяются к ОБЕИМ сторонам. Пин: task_log с многострочным сообщением → export → import dry-run добавляет 0 строк; повторно — тоже 0. НЕГАТИВ: РЕАЛЬНО новая строка журнала в файле по-прежнему добавляется; НЕГАТИВ: две записи, различающиеся только пробелами/переводами строк, считаются ОДНОЙ, а различающиеся текстом — двумя. ЯВНОЕ ОГРАНИЧЕНИЕ в CHANGELOG: импорт в пустую БД по-прежнему кладёт схлопнутое сообщение — устраняется дублирование при реимпорте, а не лоссовость дизайна.
2. D3 ПОРЯДОК СПИСКОВ: tags сравниваются через ту же канонизацию, что и экспорт (sorted). Пин: несортированные теги в БД → export → dry-run 0 updated. НЕГАТИВ: реально другой набор тегов по-прежнему updated.
3. D4 ВРЕМЕННЫЕ МЕТКИ: datetime-колонки сравниваются через normalize_ts на обеих сторонах ('…Z' ≡ '…+00:00' ≡ SQLite-пробельная форма). НЕГАТИВ: реально разные моменты по-прежнему считаются изменением; неразбираемое значение не роняет импорт.
4. D5 ОТСУТСТВИЕ ≠ NULL: колонка, чей ключ ОТСУТСТВУЕТ во frontmatter, исключается из дельты целиком. Явно пустое значение (`key: []`, `key: null`) остаётся легитимной очисткой. Пин: файл без relevant_files + БД со списком → 0 updated, реальный import НЕ обнуляет; НЕГАТИВ: явное `relevant_files: []` ОБНУЛЯЕТ.
5. СТОЯЧИЙ ГЕЙТ вместо разового замера: тест на сгенерированном покрывающем дереве (все типы сущностей, многострочный журнал, кириллица, несортированные теги, оба формата времени, отсутствующие поля) требует, чтобы dry-run импорт свежесделанного экспорта был ПУСТ по всем четырём счётчикам. Тест обязан ПАДАТЬ на коде до фикса — прогнать и зафиксировать вывод в журнале задачи.
6. D1 ХОЛОДНЫЙ СТАРТ: sync_suggested укладывается в свой watchdog на ПЕРВОМ вызове session_open после старта MCP-сервера. Измерить холодную стоимость до/после; зафиксировать механизм и ПОЧЕМУ он не возвращает риск зависания /start.
7. ЗАМЕР НА ЖИВОМ ДЕРЕВЕ до/после с объяснением КАЖДОГО оставшегося расхождения.
8. Полный scoped verify зелёный: pytest, ruff, mypy, filesize; bootstrap redeploy --ide all.
9. БЕЗОПАСНОСТЬ (дерево tausik/ приходит из git pull = НЕДОВЕРЕННЫЙ ВВОД): (a) канонизация сравнения НЕ ослабляет построчный якорь _JOURNAL_RE — подделанная строка `- <ts> [phase] — …` внутри прозы не становится записью журнала; (b) `## Journal` в прозе Plan не подделывает журнал; (c) whole-batch abort на битом файле не смягчён; (d) AC-4 — сужение привилегии: недоверенный файл больше не может обнулить поле умолчанием, только явным значением. Зафиксировать (d) в CHANGELOG.
10. НАПРАВЛЕНИЕ НЕ УТВЕРЖДАЕТСЯ БЕЗ ДОКАЗАТЕЛЬСТВА (смежный дефект, найден замером AC-7). import_suggested утверждает «файлы несут стейт, которого нет в БД → предложить tausik sync», хотя непустой план доказывает лишь РАЗЛИЧИЕ. На живом дереве направление ОБРАТНОЕ (БД новее), и предложенный sync откатил бы решение #191 и переоткрыл закрытую задачу. Обоснование срочности: до этой задачи секция всегда падала по таймауту, и совет был невидим; фикс D1 впервые делает его видимым — чинить D1 и оставить несостоятельный вывод значит вывести опасный совет в интерфейс.
