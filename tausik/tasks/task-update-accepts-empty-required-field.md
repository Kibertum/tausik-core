## Goal

НАБЛЮДЕНИЕ, воспроизведено вживую в сессии #159. `tausik task update <slug> --acceptance-criteria ""` принимает ПУСТУЮ строку, стирает существующие acceptance_criteria и печатает "Task updated." — отчитывается об успехе за уничтожение данных.

КАК ПОЙМАНО. В команду подставилась незаданная переменная оболочки, аргумент пришёл пустой строкой. CLI не возразил. AC задачи v2-verify-receipt-as-argument (3581 байт, десять пунктов) были бы потеряны молча, если бы следующим шагом не была проверка ЭФФЕКТА, а не кода возврата.

ПОЧЕМУ ЭТО НЕ МЕЛОЧЬ. acceptance_criteria — вход QG-0: без них task start отказывает. Стирание AC переводит задачу в состояние, из которого её нельзя запустить, и делает это без единого слова. Тот же вопрос надо задать про --goal и --rollback-plan: они тоже входы гейтов.

ЧТО ПРОВЕРИТЬ ПЕРЕД ПОЧИНКОЙ. Форма отказа важнее найденной точки (конвенция #361): перечислить ВСЕ поля task update, чьё пустое значение сегодня проходит, и решить для каждого — пустая строка это "очистить" или "ошибка". Различие уже выражено в CLI: --notes-overwrite существует именно для намеренной перезаписи, то есть намерение очистить выражается ЯВНЫМ флагом, а не пустым аргументом.

ГРАНИЦА. Не превращать в общий валидатор аргументов: у MCP-сервера валидации нет вовсе, это отдельная задача mcp-server-drops-unknown-arguments-silently.

## Acceptance Criteria

AC1: перечислены ВСЕ строковые поля task update, чьё пустое значение сегодня проходит; для каждого записано решение 'очистить' или 'ошибка'. Форма закрыта целиком, а не только найденная точка (конвенция #361).
AC2: пустая или состоящая из пробелов строка в поле, объявленном обязательным, ОТКЛОНЯЕТСЯ с ошибкой, называющей поле; существующее значение остаётся нетронутым.
AC3: отказ происходит ДО любой записи — частичной записи не возникает (та же форма, что у батча бюджетов выше по методу).
AC4: поля, для которых очистка законна, продолжают очищаться, и это покрыто тестом — починка не превращается в запрет очистки вообще.
AC5 (негативный): проверено, что команда НЕ печатает 'Task updated.' в случае отказа; тест утверждает и сообщение об ошибке, и НЕИЗМЕННОСТЬ значения в БД, а не только код возврата. Проверка только кода возврата считается недостаточной — именно она и пропустила этот дефект.
