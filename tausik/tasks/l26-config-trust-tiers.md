## Goal

КОРЕНЬ ПОЛОВИНЫ ТАБЛИЦЫ ОБХОДОВ. .tausik/config.json — обычный файл, который агент может писать, и в нём живут выключатели принуждения: qg0.scope_hard_gate=false (gate_qg0_check.py:92-103), task_done.auto_verify=true (service_gates.py:269,304), risk.l3_block_on_high=false (risk_l3_trigger.py:90-99), severity гейтов (default_gates.py), exempt_files для filesize. Агент выключает собственный надзор одной записью в файл. Anthropic пришёл к обратному принципу и это готовая модель для копирования: репозиторий НЕ МОЖЕТ выдать себе полномочия — defaultMode auto игнорируется из .claude/settings.json, credential-masking честен только из user/managed-настроек. Нужно: разделить конфиг на тиры (managed/user vs project) и принять правило, что project-tier может только УЖЕСТОЧАТЬ (severity вверх, гейт включить), а ослабляющие ключи из project-tier игнорируются с явным предупреждением. Это закрывает обходы без единой строки нового принуждения.

## Acceptance Criteria

1. Введены трастовые тиры конфига: project (`.tausik/config.json`), user (`~/.tausik/config.json`), managed (`$TAUSIK_MANAGED_CONFIG`). Тир значения определяется его источником.
2. `load_config()` возвращает ЭФФЕКТИВНЫЙ конфиг: слои сливаются (managed > user > project), и охраняемый ключ из project-тира, ОСЛАБЛЯЮЩИЙ контроль относительно эффективного значения доверенных слоёв (или дефолта), не должен применяться — он отбрасывается.
3. Охраняемый набор v1: `qg0.scope_hard_gate`, `risk.l3_block_on_high`, `task_done.auto_verify`, `gates.<name>.enabled`, `gates.<name>.severity`, `verify_cache_ttl_seconds`. Ужесточение из project-тира проходит без изменений (пример из живого конфига: `gates.mypy.enabled=true` при дефолте false — остаётся true).
4. Отбрасывание НЕ молчаливое: каждое отклонение даёт запись с именем ключа, отклонённым и применённым значением; список отклонений виден в `tausik doctor`.
5. Писатели конфига (`ProjectService.gate_enable/gate_disable`, MCP `_handle_gate_toggle`, brain `_ConfigOps`) читают СЫРОЙ project-слой, а не эффективный — иначе при сохранении значения user/managed-тиров протекут в файл проекта.
6. `gates disable` охраняемого гейта не должен молча рапортовать успех: возвращает явное сообщение, что запись отклонена политикой тиров.
7. Негативные сценарии (тесты): отсутствующие user/managed конфиги → поведение идентично текущему; некорректный (битый) JSON в user/managed → предупреждение и игнор слоя, без падения; пустой project-конфиг → дефолты; ослабляющий ключ из project-тира не должен применяться; ослабляющий ключ из user-тира применяется (тир доверенный).
8. БЕЗОПАСНОСТЬ — поверхность угроз явно зафиксирована в докстринге модуля и в доке, включая ЧЕСТНЫЕ границы: (а) закрываемая угроза — репозиторий НЕ МОЖЕТ выдать сам себе полномочия: `.tausik/config.json` едет вместе с клоном/PR, `~/.tausik/config.json` не едет; (б) НЕ закрывается — агент с Bash может писать в user-тир и в env `TAUSIK_MANAGED_CONFIG`, тир повышает планку и делает обход видимым в diff, но не является песочницей; это записано, а не замолчано. Проверяется тестом на docstring-контракт и ревью доки.
9. БЕЗОПАСНОСТЬ — устойчивость загрузчика доверенных слоёв: путь user-конфига берётся из `expanduser`, читается только как обычный файл; отсутствующий, битый, не-объектный (JSON-массив/скаляр) или нечитаемый по правам слой не должен ронять фреймворк и не должен молча повышать полномочия — слой игнорируется с предупреждением, политика остаётся в силе. Покрыто тестами по каждому случаю.
10. `ruff check scripts/ tests/` чист; обе линии pytest зелёные (быстрая и `-m slow`); `python scripts/gen_doc_constants.py --check` проходит; бейджи тестов в README.md и README.ru.md обновлены.
