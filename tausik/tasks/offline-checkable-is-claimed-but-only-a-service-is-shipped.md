## Goal

Утверждение README об офлайновой проверке либо подкреплено работающим путём без сети и закреплено тестом, либо заменено на правду о том, что есть.

## Acceptance Criteria

1. Замер зафиксирован: README.md строки 65 и 129 обещают «verify it offline» и «offline-checkable», тогда как docs/en/no-sdk-verify.md описывает ТОЛЬКО HTTP-сервис (Quickstart, Endpoints, POST /verify, клиент на http.client, сниппет GitHub Actions) и слова offline не содержит вовсе.
2. Принято и записано решение из двух: либо (а) поставляется путь проверки БЕЗ СЕТИ — автономный скрипт на stdlib, принимающий квитанцию и публичный ключ и не открывающий сокетов; либо (б) формулировка README исправляется на то, что есть на самом деле. Третьего — оставить как есть — НЕТ.
3. Если выбран путь (а): офлайновость ЗАКРЕПЛЕНА ТЕСТОМ, а не обещанием. Приём заимствован у HELM AI Kernel: их тест обходит граф импортов верификатора и ломает сборку при появлении транспортного пакета. Наш эквивалент — тест, проверяющий, что модуль офлайн-проверки не импортирует ни socket, ни urllib, ни http, ни ssl, ни requests, ни транзитивно.
4. Документация и README приведены в соответствие с фактом на ОБОИХ языках.
5. НЕГАТИВНЫЙ сценарий: тест обязан ПАДАТЬ, если в модуль верификатора добавить импорт socket. Проверяется мутацией, иначе он охраняет пустоту.
6. НЕГАТИВНЫЙ сценарий: путь (а) НЕ имеет права требовать ключ из самой квитанции. Ключ приходит из локального хранилища или явным аргументом — как сегодня в verify_receipt. Ключ, едущий вместе с тем, что он удостоверяет, не является корнем доверия.
7. НЕГАТИВНЫЙ сценарий: обещание не восстанавливается раньше механизма. Пока путь (а) не поставлен, в README стоит формулировка (б).
