## Goal

ПЕРВАЯ задача эпика team-state-in-git — всё downstream зависит от формата, поэтому его надо зафиксировать до кода. Спроектировать и записать в docs/{ru,en}/ спецификацию git-native проекции состояния TAUSIK:

(1) Раскладка каталога (напр. tausik/tasks/&lt;slug&gt;.md, decisions/&lt;slug&gt;.md, memory/&lt;slug&gt;.md, epics/, stories/). Один файл на сущность — чтобы правки двух инженеров на разных задачах мёржились чисто, а конфликт локализовался в одну сущность.
(2) Формат файла: markdown + YAML-frontmatter. Точно определить, какие поля идут во frontmatter (машинные: slug, status, ids связей), а какие в тело (goal, AC, план, журнал). Журнал задачи — append-only секцией, чтобы сливался как добавленные строки.
(3) Контракт round-trip: экспорт(БД)→файлы и импорт(файлы)→БД обязаны быть обратными. Определить канонический порядок полей, нормализацию (переводы строк, сортировка списков, стабильные даты), чтобы один и тот же стейт давал байт-идентичный файл на любой машине — иначе diff шумит и мержи ложно конфликтуют.
(4) Границы объёма (решение владельца): В git едут tasks, task_logs, epics, stories, decisions, memory, memory_edges. НЕ едут: verification_runs, gate_runs, reviews, sessions, session_usage_metrics, usage_events, events(audit-chain). Для КАЖДОЙ таблицы явно записать: едет / не едет / почему.
(5) Стратегия слияния и конфликтов: что происходит при git merge двух веток (разные сущности — чисто; одна сущность — конфликт в одном файле). Как трактовать удаления и переименования слагов.

Выход: docs/ru/team-state-in-git.md + зеркало en, плюс запись spec в БД (tausik spec). Кода-реализации в этой задаче нет — только контракт, на который ссылаются задачи 2–6.

## Acceptance Criteria

1. docs/ru/team-state-in-git.md + зеркало docs/en/team-state-in-git.md описывают точную раскладку каталога (шаблон пути для каждой сущности), формат файла (какие поля во frontmatter, какие в теле), с ПРИМЕРОМ реального файла задачи и файла решения.
2. Контракт round-trip записан явно и как ПРОВЕРЯЕМОЕ свойство: правила нормализации (канонический порядок полей, сортировка списков, переводы строк LF, формат дат), гарантирующие байт-идентичность экспорта на любой машине и при повторном экспорте.
3. Таблица объёма: для КАЖДОЙ таблицы БД указано едет-в-git / не-едет / почему; согласуется с решением владельца (tasks, task_logs, epics, stories, decisions, memory, memory_edges едут; verification_runs, gate_runs, reviews, sessions, session_usage_metrics, usage_events, events-audit — нет).
4. Стратегия слияния: описано поведение git merge для разных сущностей (чисто) и одной сущности (конфликт в одном файле), трактовка удаления сущности и переименования слага.
5. НЕГАТИВНЫЕ И ГРАНИЧНЫЕ сценарии описаны явно: (а) сущность без стабильного слага до миграции — экспортировать нельзя, зависимость от state-git-stable-ids названа; (б) недетерминированное поле (порядок тегов/связей) — правило нормализации обязано устранить недетерминизм; (в) файл с НЕВАЛИДНЫМ frontmatter, отредактированный руками — импорт обязан сообщить об ошибке, а не молча проглотить.
6. Контракт записан как spec в БД (tausik spec add) со ссылкой на эпик team-state-in-git, чтобы задачи 2-6 ссылались на него как на источник правды формата.
