## Goal

Перед тем как писать код, задан и записан вопрос, нужен ли он. Сейчас у нас есть жёсткое 'нет кода без задачи', но нет ничего про 'нет кода без необходимости'.

## Acceptance Criteria

AC1. СИГНАЛ (закладка 2026-06-16): скилл Ponytail заставляет агента сначала проверить, нужен ли код вообще, затем поискать решение в стандартной библиотеке или родных возможностях, и только потом писать своё. Порядок здесь и есть содержание.
AC2. У НАС ЭТА ДЫРА ИЗМЕРИМА, И ЧИСЛО ЕСТЬ. Сессия #177: закрыта одна задача, заведено шесть. Решение #245 остановило этот режим. Задача обязана начать с замера, а не с механизма: какая доля наших задач за последние N сессий добавляла код там, где хватило бы правки документа, настройки или отказа.
AC3. МЕХАНИЗМ НЕ ИМЕЕТ ПРАВА СТАТЬ ЕЩЁ ОДНИМ ОБЯЗАТЕЛЬНЫМ ПОЛЕМ. У нас уже есть QG-0 с целью и критериями приёмки. Если вопрос встраивается туда — встроить туда, а не заводить седьмой гейт. Лишний гейт заполняют не глядя, и он перестаёт значить что-либо.
AC4. НЕГАТИВНЫЙ СЦЕНАРИЙ: механизм не должен блокировать задачу, где код очевидно нужен. Проверка обязана быть дешёвой в очевидном случае, иначе её начнут обходить, и мы получим обход вместо дисциплины.
AC5. НЕГАТИВНЫЙ СЦЕНАРИЙ: ответ 'код не нужен' обязан вести к ЗАКРЫТИЮ задачи отказом с записанной причиной, а не к её зависанию. Иначе мы заменим лишний код лишними висящими задачами.
AC6. Проверить, не покрывает ли это частично уже существующее: dead-end, отказ по замеру, ограничение объёма. Дублирующий механизм хуже отсутствующего.
