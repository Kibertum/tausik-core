## Goal

ЗАМЕР СМЕНЫ #225, ЖИВОЕ ДЕРЕВО. Релиз 1.9 собирается обещать существенную экономию токенов. Сегодня этого числа НЕТ, и главное — его нечем получить. Четыре измерения, все на .tausik/token_metrics.jsonl и `tausik metrics`:

(1) ВХОДНЫЕ ТОКЕНЫ НЕ ИЗМЕРЯЮТСЯ ВООБЩЕ. 4777 строк ленты, из них строк с input_tokens > 2 — НОЛЬ. Поле стоит константой 2 у каждого события, поэтому колонка in_total в `metrics tokens` есть просто удвоенное число вызовов. Экономия входного контекста — ровно то, что обещается, — не наблюдаема ни в одной записи.

(2) ЛЕНТА ПОКРЫВАЕТ 5 СМЕН ИЗ 225 (2.2%). В файле ровно session_id 220-224, всё за двое суток. Ротация здесь ни при чём: потолок TOKEN_METRICS_MAX_BYTES = 32 МБ, а файл весит 896 КБ — то есть данные исчезают ЗАДОЛГО до предела, и почему именно — не выяснено. Продольного ряда, на котором можно показать «стало дешевле», не существует.

(3) СУММА CACHE_READ НЕ ЕСТЬ РАСХОД. Собственная шапка `metrics tokens` это и говорит: цифры message-level, проштампованные на инструмент, а суммирование cache_read пересчитывает один и тот же кэшированный контекст на каждом вызове. Сумма по 5 сменам — 2 247 439 021, читать её как потребление нельзя.

(4) БАЗЫ СРАВНЕНИЯ НЕТ НИ ОДНОЙ. Ни одного замера «без TAUSIK» и ни одного «до/после» для рычагов экономии. Единственный процент в дереве — «~65%» у caveman в quickstart, и там честно написано, что это ИХ цифра и в среде TAUSIK не измерена.

ЧТО ИЗ ЭТОГО СЛЕДУЕТ ДЛЯ РЕЛИЗА: обещание экономии публиковать нельзя, пока нет прибора. README сегодня экономию НЕ обещает — это надо сохранить до появления числа, а не наоборот.

ЧТО ДЕЛАЕТСЯ: прибор до обещания. (а) выяснить и починить, почему input_tokens приходит константой 2 — и если харнесс этого поля не отдаёт, записывать ОТСУТСТВИЕ, а не 2 (решение #334); (б) выяснить, почему лента теряет смены при 3% заполнения потолка; (в) определить, что именно называется экономией, и завести хотя бы одну пару «до/после» на реальном рычаге; (г) цифра, которую нельзя получить, докладывается как «не измерено», а не как ноль.

НЕГАТИВНЫЙ СЦЕНАРИЙ: прибор, показывающий уверенное число там, где данных нет, хуже отсутствия прибора — ровно этим сейчас и болеет `metrics` (см. pricing-guard-watches-routable-models-not-the-running-one: 36.5% токенов оценены в $0.00 при зелёном тесте). Тест обязан проверять, что при отсутствии данных отчёт говорит «не измерено» и НЕ печатает ноль.

ГРАНИЦА: измерение расхода MCP-поверхности — mcp-tool-surface-costs-44kb-of-schema-per-turn; сокращение расхода — no-byte-cap-rule-for-command-output-anywhere и repeated-reads-are-paid-for-in-full-every-time. Здесь ПРИБОР, а не рычаги. Не сливать.

## Acceptance Criteria

ЗАМЕР СМЕНЫ #227 ИСПРАВИЛ ПОСТАНОВКУ. Поле input_tokens НЕ стоит константой по вине писателя: Anthropic API при включённом кэше действительно возвращает input_tokens=2, потому что весь контекст ушёл в cache_read_input_tokens + cache_creation_input_tokens, а input_tokens — лишь НЕОХВАЧЕННЫЙ КЭШЕМ ОСТАТОК. Значение истинно и бесполезно; дефект прибора в том, что отчёт НАЗЫВАЕТ его входом и суммирует как вход. Записывать «отсутствие» тут нечего — надо записывать ВЕЛИЧИНУ, КОТОРУЮ СЕГОДНЯ ВЫБРАСЫВАЮТ. Попутно найдена поломка крупнее заявленных: 72.4% строк ленты (3840 из 5301) — межсессионные ДУБЛИКАТЫ, сумма cache_read раздута ровно в 2.03 раза.

AC1. АТРИБУЦИЯ ПО ВРЕМЕНИ, А НЕ «САМАЯ СВЕЖАЯ В БД». Строка ленты несёт ту сессию, в интервал [started_at, ended_at] которой попадает её ts. Сегодня resolve_session_id() отдаёт SELECT id ORDER BY id DESC LIMIT 1, а extract_token_rows заново обходит ВЕСЬ транскрипт на каждом SessionEnd — поэтому сессии 221, 222 и 223 имеют одинаковый первый ts 2026-09-06T16:13:29.282Z, а сессия 223 длиной 25 минут несёт 1409 строк за 16 часов. Тест: транскрипт, пересекающий три сессии, даёт три НЕПЕРЕСЕКАЮЩИХСЯ набора.

AC2. ts ВНЕ ЛЮБОГО ИНТЕРВАЛА СЕССИИ ДАЁТ ОТСУТСТВИЕ (session_id=null), А НЕ ДОГАДКУ (решение #334). Тест на строку раньше первой сессии и на строку в разрыве между сессиями.

AC3. ЛЕНТА НЕСЁТ РАЗМЕР ВХОДНОГО КОНТЕКСТА. Новое поле context_tokens = input_tokens + cache_creation_input_tokens + cache_read_input_tokens на сообщение, поделённое между tool_use тем же правилом, что и остальные (остаток последнему). Если usage отсутствует или не несёт полей — null, НЕ 0. Именно эта величина, а не input_tokens, есть предмет обещания экономии.

AC4. ДУБЛИКАТОВ НЕТ. Тест утверждает на НАСТОЯЩЕЙ ленте проекта (не на фикстуре): ни один кортеж (ts, tool_name, output_tokens) не встречается под двумя разными session_id. Сегодня таких кортежей 1336.

AC5. ОТЧЁТ НЕ ПЕЧАТАЕТ НОЛЬ ВМЕСТО «НЕ ИЗМЕРЕНО». Величина, которой в данных нет (context_tokens=null, session_id=null, пустая лента), выводится словами «не измерено»/«n/a», а не нулём. Тест: лента без context_tokens → отчёт содержит маркер отсутствия и НЕ содержит 0 на этом месте. Негативный сценарий задачи: прибор, уверенно печатающий число там, где данных нет, хуже отсутствия прибора.

AC6. ОТЧЁТ ПЕЧАТАЕТ ЧЕСТНУЮ ШИРИНУ РЯДА: сколько сессий существует в БД, за сколько из них есть строки, и с какого ts. Без этого утверждение «продольный ряд» непроверяемо; сегодня отчёт говорит «5 session(s) observed total», умалчивая, что сессий 227.

AC7. ОПРЕДЕЛЕНИЕ ЭКОНОМИИ ЗАПИСАНО РЕШЕНИЕМ: какая величина называется экономией, относительно какой базы она считается, каким прибором снимается и что делать, когда база отсутствует. Обещание экономии в README не появляется, пока нет числа (состояние README сохраняется).

ГРАНИЦА СОХРАНЯЕТСЯ: здесь прибор. Рычаги (MCP-поверхность, потолок вывода, повторные чтения) — в своих задачах, не сливать.

AC8 (БЕЗОПАСНОСТЬ). ПОВЕРХНОСТЬ УГРОЗЫ: прибор читает транскрипт агента — файл, содержащий произвольный пользовательский ввод, вывод инструментов и потенциально секреты. Свойство, которое обязано сохраниться: в ленту попадают ТОЛЬКО имя инструмента, метка времени, числа и имя модели — НИКОГДА аргументы вызова, содержимое tool_result, текст сообщений и пути. Тест: транскрипт с секретом в аргументе инструмента и в тексте ассистента даёт строки ленты, НЕ содержащие этой подстроки. Второе: чтение sessions из .tausik/tausik.db — только SELECT, только read-only соединение, отказ БД (locked/missing) даёт отсутствие атрибуции, а не падение хука (хук не имеет права ломать вызов, который он сопровождает).
