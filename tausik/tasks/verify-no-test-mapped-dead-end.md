## Goal

Преемник cli-verify-bypasses-cache-guards: закрывает AC4, AC5 и AC6, оставшиеся невыполненными при её закрытии (см. поправку в журнале той задачи).

ГЛАВНОЕ (AC4). Пока CLI обходил защиты, документационные и конфигурационные задачи закрывались так: verify по CHANGELOG.md давал прогон, где все гейты [SKIP], строка писалась кэшируемым зелёным, task done закрывался по кэш-хиту. Это была дыра, и она закрыта. Но на сервисном пути тупик существовал и до этого, а теперь он на ОБОИХ путях: набор, не мапящийся ни на один тест, даёт no-test-mapped и выход 1, то есть закрыть такую задачу нельзя ничем.

Доказано тестом, а не рассуждением: tests/test_cli_verify_guards.py::TestAllSkippedRunParity с DECLARED=[CHANGELOG.md, CHANGELOG.ru.md] — обе ветки блокируют. Живой прецедент — прогон #1054 ровно этой формы.

ЦЕНА БЕЗДЕЙСТВИЯ КОНКРЕТНА. В релизе 1.8 документационные задачи составляют заметную долю: kb-docs-map, kb-docs-swarm, kb-docs-consistency, l26-narrative-honesty, release-18-breaking-change-notes. Ни одна из них сейчас не закрывается.

СООБЩЕНИЕ БЛОКИРОВКИ ВРЁТ ОТДЕЛЬНО. Оно предлагает «Add tests/test_<basename>.py or pass --no-knowledge if intentional». Флаг no_knowledge (service_task_done.py:280-301) управляет исключительно требованием захвата знаний и на гейты не влияет — проверено grep-ом. Агенту называют выход, которого нет; для этого проекта неверная подсказка по устранению — дефект сам по себе, а не текст.

ТРЕБОВАНИЕ К РЕШЕНИЮ. Нужен ЯВНЫЙ и ЗАПИСЫВАЕМЫЙ выход, а не молчаливый. Разница между дырой и легальным путём здесь не в том, можно ли закрыть задачу без тестов, а в том, остаётся ли от этого след, по которому потом можно посчитать, сколько закрытий прошло без выполненного гейта. Предпочтительная форма: осознанное объявление на прогоне, которое попадает в строку verification_runs отличимым признаком (например, собственный scope-лейбл), чтобы выборка «все закрытия без реального гейта» была одним запросом. Молчаливое исключение по расширению файла не принимается: оно возвращает ровно ту невидимость, которую закрыла родительская задача.

## Acceptance Criteria

AC1. Тупик снят: задача, чьи relevant_files не мапятся ни на один тест, имеет способ закрыться, и он объявляется ЯВНО на прогоне, а не выводится из типа файлов. Покрыто тестом на обоих путях записи (CLI и run_gates_with_cache).
AC2. Использование этого выхода оставляет след, отличимый одним SQL-запросом: строка verification_runs несёт признак, по которому выбираются все закрытия, прошедшие без единого выполненного гейта. Покрыто тестом, проверяющим сам запрос.
AC3. Без явного объявления поведение не меняется: прогон, где все гейты пропущены, по-прежнему блокирует и по-прежнему не порождает пригодного для повтора зелёного. Негативный тест обязателен — иначе выход превращается в дефолт.
AC4. Сообщение блокировки no-test-mapped называет ТОЛЬКО существующие механизмы. Упоминание --no-knowledge удалено или заменено. Покрыто тестом, сверяющим текст сообщения с фактически принимаемыми флагами.
AC5. Наследство от родительской задачи: полносуитный tausik verify без --task по-прежнему не порождает строки, пригодной для кэш-поиска. Покрыто тестом (родительская задача проверила это только чтением кода).
AC6. Наследство от родительской задачи: строки, записанные CLI-путём ДО фикса, не принимаются задним числом. Ожидаемое обоснование — TTL 600 с в verify_constants.DEFAULT_CACHE_TTL_S отбраковывает их независимо от files_hash. Закрепить тестом и написать явно, а не оставлять выводом из чтения.
AC7. Полный pytest (обе линии, включая -m slow) зелёный, ruff чистый, CHANGELOG EN+RU обновлены.

## Rollback

git revert коммита задачи. Схема БД не меняется — признак кодируется значением существующей колонки scope, миграции нет, откатывать нечего. Строки, записанные с этим признаком до отката, останутся в verification_runs и после него читаются как обычные прогоны с нестандартным лейблом scope; данные не портятся. Поведенческий откат без revert: не передавать новый флаг — без него ветка не активируется вовсе (это закреплено негативным тестом AC3).
