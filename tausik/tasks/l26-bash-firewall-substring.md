## Goal

Тот же класс бага, что исправлен в git_push_gate 2026-07-18 (память #213). bash_firewall.py:97-99 сравнивает BLOCKED-паттерны как подстроки в нижнем регистре, поэтому блокирует любую команду, где опасная фраза встречается в ТЕКСТЕ аргумента. ВОСПРОИЗВЕДЕНО ВЖИВУЮ 2026-07-18: попытка завести эту самую задачу через tausik task add была заблокирована, потому что в тексте цели упоминалась SQL-фраза удаления таблицы. WARN-паттерны (:62-79) уже переведены на якорные regex — BLOCKED-список забыли. Привести к тому же подходу: токенизация shlex или якорные regex + консервативный fallback при неразбираемой команде. Регресс-тесты: упоминание опасной фразы в кавычках-аргументе проходит, реальная опасная команда блокируется.

## Acceptance Criteria

1. BLOCKED-паттерны больше не срабатывают на фразу, лежащую в кавычках как ДАННЫЕ для программы, которая аргументы не исполняет. 2. FALSE-POSITIVE устранён: tausik task log или memory add с опасной SQL-фразой в тексте цели проходит (returncode 0) — воспроизведено вживую 2026-07-18 дважды. 3. TRUE-POSITIVE сохранён для интерпретаторов: sqlite3 с SQL в кавычках блокируется, потому что вызываемая программа свои аргументы ИСПОЛНЯЕТ (существующий тест drop_table_blocked обязан остаться зелёным). 4. НЕГАТИВНЫЙ СЦЕНАРИЙ: bash -c с опасной командой в кавычках блокируется, а echo с той же фразой не блокируется — разница именно в исполняющей программе. 5. Неразбираемая команда (несбалансированные кавычки) обрабатывается консервативно: сканируется целиком. 6. Все существующие тесты TestBashFirewall остаются зелёными; ruff чист; прогон на 3.11 и 3.13.
