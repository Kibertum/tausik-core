## Goal

ЗАМЕР (смена #210, найдено ПОСЛЕ закрытия родительской задачи, при заведении долгов):
docs/en/mcp.md:146 и docs/ru/mcp.md:143 — описание tausik_adapt_sign по-прежнему говорит «both roles => signed» / «обе роли => signed».
docs/en/cli.md:259 и docs/ru/cli.md:269 — описание детектора дрейфа по-прежнему говорит «signed <-> dual signature» / «signed <-> двойная подпись».
Все четыре описывают ПОВЕДЕНИЕ, КОТОРОГО БОЛЬШЕ НЕТ: v50 перевёл статус в approved, и sign() пишет approved. Документация лжёт о том, что вернёт живая команда.

Root cause (инвентарь): инвентарь носителей по докам снимался ПО ФОРМЕ СПИСКА, а не по ЗНАЧЕНИЮ. Я искал «draft.*signed» и «signed.*superseded», то есть перечень целиком, и нашёл ровно два места — таблицы adapt_list. Одиночное вхождение значения («=> signed», «signed <-> подпись») под такой шаблон не подпадало ни в одном из четырёх файлов. Это тот же класс промаха, что стоил #209 отдельной задачи: инвентарь по УДОБНОЙ ФОРМЕ вместо НИЖНЕГО ЭЛЕМЕНТА. В коде я правило применил — искал голый литерал; в доках не применил.

Prevention: инвентарь носителей ЗНАЧЕНИЯ снимай ПО САМОМУ ЗНАЧЕНИЮ, а не по контейнеру, в котором его удобно искать, и в docs/ тем же шаблоном, что и в коде. Механическая часть профилактики — задача doc-values-of-closed-lists-have-no-guard: значение закрытого перечня, названное в документации, обязано сверяться с источником, а не жить копией.

## Acceptance Criteria

AC-1: Ни один файл в docs/ не описывает статус ADAPT «signed» как результат двойной подписи; все четыре носителя (docs/en/mcp.md, docs/ru/mcp.md, docs/en/cli.md, docs/ru/cli.md) называют approved.
AC-2: Негативный сценарий — поиск по ЗНАЧЕНИЮ (а не по форме списка) в docs/ не возвращает ни одного вхождения «signed» в смысле статуса ADAPT; ошибочные совпадения про подписанные расписки и ed25519 отделены явно и перечислены.
AC-3: Проверка воспроизводима командой, а не глазами: приведён точный grep, которым снят замер до и после.
