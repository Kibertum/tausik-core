## Goal

ПРЕМИСА ИЗ ПЕРЕДАЧИ #207. Кочует третью смену подряд, НЕ ПРОВЕРЕНА ЗАМЕРОМ НИ РАЗУ, включая #210.
Утверждение: инструментальный канал PowerShell не выполняет либо не отдаёт вывод python -c. Практическое следствие, если верно: однострочные проверки через python -c ненадёжны в этом канале, и всякий замер надо писать ФАЙЛОМ — что согласуется с уже действующим правилом «команду с вложенными кавычками писать файлом».
ПЕРВЫЙ ШАГ — ЗАМЕР, А НЕ ПОЧИНКА: воспроизвести отказ и зафиксировать ТОЧНУЮ форму. Кавычки? Кодировка? Ненулевой код возврата — или ПУСТОЙ STDOUT ПРИ НУЛЕВОМ? Последнее самое опасное: пустой вывод при rc=0 читается вызывающим как «проверка прошла, находок нет», то есть отказ инструмента маскируется под отрицательный результат замера. Именно этот класс мы весь релиз и вычищаем.
ЕСЛИ ПРЕМИСА НЕ ПОДТВЕРДИТСЯ — закрыть с записью и убрать пункт из передач, как и changelog-gate-double-registration-premise-unconfirmed.
ВНЕ ОБЪЁМА 1.9: инфраструктура инструментального канала, не норма RENAR.

## Acceptance Criteria

AC-1: замер в канале PowerShell зафиксирован в журнале задачи с точной формой каждого вызова: простой print, вложенные двойные кавычки через \", одинарные снаружи и двойные внутри, кириллица под -X utf8, sys.exit(3), необработанное исключение — с stdout и $LASTEXITCODE каждого.
AC-2: ответ на главный вопрос задачи дан прямо: есть ли форма, при которой stdout пуст при rc=0 (отказ маскируется под «находок нет»). Если нет — премиса снята с записью.
AC-3: если премиса не подтвердилась — задача закрыта без правок, пункт снят из передач, а настоящая форма отказа (какая именно и насколько громкая) записана в память с указанием на действующую конвенцию «команду с вложенными кавычками писать файлом».
