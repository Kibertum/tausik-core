## Goal

Обнаружено в сессии #115 при закрытии l26-gate-command-neutering.

Наблюдение: verify --task записал зелёный (status=miss), затем был отредактирован scripts/project_config.py — файл, который затем объявлен в relevant_files при task done, — и повторный verify вернул status=hit. Кэш правку не заметил.

Причина не в 4-КиБ окне (решение #140): compute_files_hash включает mtime_ns и size, любая обычная запись их двигает. Причина в том, что на момент verify у задачи ещё НЕТ relevant_files: их сообщает только task done. compute_files_hash от пустого списка возвращает стабильный empty-marker hash (документировано в докстринге как «Empty list → stable empty-marker hash»), поэтому зелёный оказывается привязан к пустому множеству файлов и остаётся валидным в пределах TTL при ЛЮБЫХ правках дерева.

Последствие: последовательность verify → правка → task done проходит QG-2 по зелёному, снятому ДО правки. Это ровно тот класс тихого зелёного, против которого писалась честность чека в l26-verify-git-diff-wire.

Смягчающее обстоятельство (проверить, насколько оно покрывает): task done в этом сценарии показал cache_status=git-mismatch, то есть кросс-чек с git расхождение УВИДЕЛ. Но по решению #138 расхождение намеренно не блокирует, так что зелёный был засчитан.

Задача: (а) воспроизвести на тесте — verify без relevant_files, правка файла, повторный verify обязан дать miss, а не hit; (б) решить, чем чинить. Варианты: verify --task без объявленного scope не кэширует вовсе (по аналогии с полносуитным verify, который уже не кэшируется); либо scope для кэша берётся из git-диффа, когда relevant_files пусты; либо пустой scope трактуется как «неизвестно» и наследует контракт деградации памяти #226 — «неизвестно» не равно «пусто», а гейт, не сумевший вычислиться, обязан блокировать (#221). Третий вариант выглядит наиболее согласованным с уже принятыми конвенциями.

Негативный сценарий: починка не должна ломать полносуитный verify без task_slug (он и так не кэшируется) и не должна заставлять агента объявлять relevant_files дважды.
