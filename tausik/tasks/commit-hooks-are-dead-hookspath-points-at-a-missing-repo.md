## Goal

В .git/config ЭТОГО репозитория стоит core.hooksPath = D:\Work\Personal\claude\.git\hooks. Ни каталога, ни репозитория D:/Work/Personal/claude на машине нет. Задокументированное значение для dev-репозитория — scripts/hooks (docs/ru/hooks.md:86, docs/en/hooks.md:79). Следствие ЗАМЕРЕНО, а не предположено: `git hook run pre-commit` при текущей настройке отвечает «cannot find a hook named pre-commit» (exit 1), при -c core.hooksPath=scripts/hooks — исполняет хук целиком (exit 0). git commit трактует ненайденный хук как ОТСУТСТВИЕ хука и не говорит ничего. Значит на каждом коммите в этом репозитории НЕ РАБОТАЮТ: (1) gate_memory_route — блокирующий контроль безопасности, тот самый, про который docs/en/security.md обещает, что он «IDE-agnostically» стережёт рабочее дерево от утечки проектного знания в чужую память агента; (2) mypy; (3) инкрементальный переиндекс RAG. Собственный .git/hooks/pre-commit в репозитории есть (от 2026-03-04, «KAI pre-commit hook»), но при заданном hooksPath git на него не смотрит вовсе. Это ровно тот класс, к которому у проекта заявлена нулевая толерантность: контроль не выключен решением, он МЁРТВ молча. Ограничение «нет коммита без gates» из CLAUDE.md на этом дереве машиной не обеспечено ничем — только дисциплиной агента, вручную зовущего gate_runner.

## Acceptance Criteria

AC1. Названо машиной, а не человеком: существует проверка, которая КРАСНЕЕТ, когда путь из core.hooksPath не содержит исполняемого pre-commit. Проверка обязана отличать три состояния — хук исполняется / хук выключен решением (core.hooksPath снят или --no-verify) / путь задан и МЁРТВ. Третье состояние — единственное красное.
AC2. Диагностика попадает в `tausik doctor`: doctor называет фактическое значение core.hooksPath, отвечает, разрешается ли по нему pre-commit, и при мёртвом пути печатает задокументированную починку (git config core.hooksPath scripts/hooks для dev-репозитория, .tausik-lib/scripts/hooks для потребителя).
AC3. НЕГАТИВНЫЙ СЦЕНАРИЙ, ОБЯЗАТЕЛЕН. Проверка НЕ ИМЕЕТ ПРАВА краснеть на репозитории, где core.hooksPath не задан вовсе: docs/ru/hooks.md:107 прямо предписывает такое состояние для CI-раннеров без mypy. Тест обязан предъявить оба случая на ВРЕМЕННЫХ репозиториях: (а) hooksPath не задан -> зелено; (б) hooksPath задан и указывает в несуществующий каталог -> красно с названным путём. Настоящее рабочее дерево в этих тестах не участвует — при провале тест испортил бы конфиг репозитория, в котором идёт работа.
AC4. Мутация обязательна: с возвращённым дефектом (hooksPath -> несуществующий каталог) проверка КРАСНАЯ и называет путь; после возврата — зелёная. Возврат побайтовой копией со сверкой, git checkout запрещён.
AC5. Настройка на этой машине починена ОТДЕЛЬНЫМ явным действием владельца и зафиксирована в журнале задачи вместе с датой: до починки — «cannot find a hook named pre-commit», после — исполнение хука целиком. Агент правит чужой git-конфиг только по явному «да».
AC6. Дефект описан в CHANGELOG.md и CHANGELOG.ru.md прозой: контроль был мёртв молча, сколько именно коммитов прошло мимо него — назвать честно «неизвестно, mtime .git/config = 2026-08-26 08:54 есть лишь верхняя граница», а не выдумывать число.

## Rollback

Проверка новая и изолированная: откат — git revert коммита задачи; doctor теряет один пункт, поведение коммита не меняется, потому что проверка ничего не блокирует, а только сообщает. Настройка git config откатывается одной командой: git config --unset core.hooksPath (либо возврат прежнего значения, записанного в журнал задачи до правки).
