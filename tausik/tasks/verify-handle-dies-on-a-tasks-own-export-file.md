## Goal

НАЙДЕНО В СЕССИИ #191 ПРИ ЗАКРЫТИИ four-accepted-adrs-were-never-assessed. ВОСПРОИЗВЕДЕНО ДВАЖДЫ, не предположено. Если задача объявляет в --relevant-files СВОЙ собственный экспорт tausik/tasks/<slug>.md, предъявить хендл нельзя НИКОГДА: сам прогон verify пишет в задачу (объявленную область, номер прогона, квитанцию), экспорт задачи от этого меняется, и хендл, покрывший этот файл, отвергается ещё до предъявления. Отказ честен и точен по формулировке — «the files this receipt covers have changed since verify run #N (files_hash A -> B). This is the substantive refusal, not a cache miss» — но условие невыполнимо в принципе, и повтор не сходится: наблюдались 870e9d910c7c -> edd0acd46e7b (первый прогон) -> e8d9e08ecc20 (второй), каждый прогон двигает хеш дальше. ОБХОД, КОТОРЫМ ЗАКРЫЛИСЬ СЕГОДНЯ: исключить из области собственный экспорт задачи, оставив семь прочих файлов. Обход работает, но он НЕ ОЧЕВИДЕН и нигде не написан, а цена ошибки — бесконечный цикл verify/done, в котором агент будет винить кэш. КЛАСС ДЕФЕКТА УЖЕ ИЗВЕСТЕН ПРОЕКТУ: конвенция #409 требует, чтобы проверка, читающая рабочее дерево, ВЫЧИТАЛА из него бухгалтерию самого фреймворка. Здесь та же болезнь в области квитанции: покрытие считается по путям, среди которых есть файл, изменяемый самим актом проверки. БЬЁТ ПО ЦЕЛОМУ КЛАССУ ЗАДАЧ: любая задача, продукт которой есть записи (разбор, вердикты, решения, планирование), естественно объявляет областью свой экспорт — и упирается в стену.

## Acceptance Criteria

AC1. Задача, объявившая областью свой собственный экспорт tausik/tasks/<slug>.md, ЗАКРЫВАЕТСЯ по хендлу — либо получает ОТКАЗ, который НАЗЫВАЕТ ПРИЧИНУ И ПОЧИНКУ («в области собственный экспорт задачи; он меняется самим прогоном verify — исключите его»), а не сообщает про изменившиеся файлы вообще. Сегодняшний отказ точен по фактам и бесполезен по действию: он не даёт понять, что условие невыполнимо в принципе.
AC2. Выбранное решение названо явно и обосновано: либо экспорт задачи вычитается из покрытия квитанции как бухгалтерия фреймворка (по конвенции #409), либо хеш покрытия снимается ДО записи прогона, либо путь запрещается в области с внятным сообщением. Молча «починить, чтобы проходило» — провал: разные решения по-разному врут о том, что именно проверено.
AC3. НЕГАТИВНЫЙ СЦЕНАРИЙ, ОБЯЗАТЕЛЕН. Починка НЕ ИМЕЕТ ПРАВА ослабить отказ в НАСТОЯЩЕМ случае: если между verify и task done изменился файл ПРОДУКТА (scripts/, tests/, harness/), хендл обязан быть отвергнут как сегодня. Тест обязан предъявить оба случая на временном проекте: (а) изменился только собственный экспорт задачи -> закрытие проходит; (б) изменился файл продукта -> отказ. Вариант (б), ставший зелёным, есть дыра в Verify-First куда хуже исходного неудобства.
AC4. Регрессия воспроизводит ИСХОДНЫЙ цикл: два последовательных verify на одной задаче с собственным экспортом в области дают РАЗНЫЕ files_hash — сегодня наблюдались 870e9d910c7c -> edd0acd46e7b -> e8d9e08ecc20. Тест обязан фиксировать несходимость ДО починки и сходимость после.
AC5. Обход задокументирован до починки: в docs/ru/agent-contract.md (раздел QG-2, edge-cases) названо, что собственный экспорт задачи в области делает закрытие невозможным. Агент, попавший в цикл, должен находить ответ, а не винить кэш.
AC6. Мутация обязательна: с возвращённым дефектом регрессия красная, после возврата побайтовой копией со сверкой sha256 — зелёная. git checkout запрещён.
