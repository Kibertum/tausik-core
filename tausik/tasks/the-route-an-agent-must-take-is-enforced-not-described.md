## Goal

ПОРУЧЕНИЕ ВЛАДЕЛЬЦА: всё построенное обязано ЖЁСТКО использоваться агентом, без отлынивания; агент должен чётко понимать путь и инструменты, которыми обязан пользоваться.

ЗАМЕР ПО СОБСТВЕННЫМ РАСШИФРОВКАМ (смена #233, 4011 команд оболочки, восемь расшифровок) — три заявленных правила, ни у одного нет механизма:

1. MCP-FIRST: разобрано 1530 вызовов CLI. У 1216 из них (79.5%) СУЩЕСТВУЕТ MCP-двойник, и всё равно вызывался shell. Крупнейшие: task update 184, task log 152, verify 116, task done 106, task show 84, task start 82, status 77, task list 69. Доля MCP среди всех обращений к фреймворку — 29.1%. Это настоящее отлынивание: маршрут есть и не выбран.

2. CLI ЧЕРЕЗ ОБЁРТКУ: 79 прямых запусков `python scripts/*.py`. Но 68 из них — к шести скриптам, для которых маршрута через обёртку НЕ СУЩЕСТВУЕТ вовсе: gen_doc_constants (41), audit_pytest_dedupe (27), senar_version_claim (6), gate_class_surface (1). То есть правило «ВСЕГДА через .tausik/tausik» здесь НЕИСПОЛНИМО. Настоящих обходов — 11 (repo_coherence, audit_closure_evidence: у них маршрут есть).

3. ПОВЕРХНОСТЬ, КОТОРУЮ АГЕНТ НЕ ВИДИТ: из 52 подкоманд CLI в тексте правил не названы 18.

ГЛАВНЫЙ ВЫВОД, И ОН МЕНЯЕТ ПОРЯДОК РАБОТ: неисполнимое правило дороже отсутствующего. Оно учит игнорировать правила вообще, а не только это одно. Поэтому сперва маршрут становится исполнимым, и только потом требуется.

ЧТО ДЕЛАЕТСЯ: (1) шесть неохваченных инструментов получают маршрут либо объявляются внутренними и отказывают на прямом запуске — третьего состояния «правило есть, выполнить нельзя» не остаётся; (2) обход существующего маршрута БЛОКИРУЕТСЯ, а не советуется; (3) MCP-first перестаёт быть надписью: вызов CLI, у которого есть MCP-двойник, называет двойника в момент выбора, а доля MCP печатается doctor'ом, чтобы её нельзя было не заметить.

ПОЧЕМУ НЕ ЖЁСТКИЙ БЛОК НА MCP-FIRST: 20.5% вызовов CLI двойника не имеют, а цепочки вида `verify && task done` и передача многострочных аргументов через файл — законные приёмы. Ложный блок на рутинной операции тренирует обход и стоит дороже пропуска (конвенция #291). Жёстко там, где однозначно; видимо там, где нет.

## Acceptance Criteria

AC1. НЕИСПОЛНИМОГО ПРАВИЛА НЕ ОСТАЁТСЯ. Каждый инструмент, который агент запускал напрямую, либо имеет маршрут через обёртку, либо ОТКАЗЫВАЕТ на прямом запуске с указанием маршрута. Состояние «правило требует, выполнить нельзя» краснеет тестом.

AC2. ОБХОД СУЩЕСТВУЮЩЕГО МАРШРУТА БЛОКИРУЕТСЯ. Прямой запуск скрипта, у которого маршрут ЕСТЬ, отклоняется и называет команду-замену. Совет тут не годится: маршрут есть, и выбор мимо него — ошибка, а не предпочтение.

AC3. MCP-FIRST НАЗЫВАЕТ ДВОЙНИКА В МОМЕНТ ВЫБОРА. Вызов CLI, у которого есть MCP-инструмент, сопровождается указанием ИМЕНИ этого инструмента. Соответствие ВЫВОДИТСЯ из таблицы диспетчеризации MCP, а не перечисляется руками.

AC4. ДОЛЯ MCP ВИДНА ЧИСЛОМ. `doctor` печатает, какая часть обращений к фреймворку шла через MCP, чтобы отлынивание было замечено, а не обнаружено через сто смен.

AC5 (НЕГАТИВНЫЙ, ГЛАВНЫЙ). ЛОЖНОГО БЛОКА НА РУТИНЕ НЕТ. Вызов CLI без MCP-двойника, цепочка команд и передача аргумента файлом НЕ блокируются и не получают упрёка. Ложный блок на рутинной операции тренирует обход и стоит дороже пропуска (конвенция #291).

AC6 (НЕГАТИВНЫЙ). ПОДСКАЗКА НЕ ПРЕВРАЩАЕТСЯ В ШУМ. Одно и то же замечание не повторяется на каждый вызов внутри смены: замечание, которое читатель научился пропускать, хуже отсутствующего.

AC7. СООТВЕТСТВИЕ CLI ↔ MCP НЕ ГНИЁТ. Оно выводится из живой таблицы MCP; запись, не совпавшая ни с одним живым инструментом, краснеет, и наоборот (решение #335).

AC8. ГРАНИЦА. Здесь НЕ добавляются новые MCP-инструменты для команд, у которых их нет, и НЕ меняется поведение существующих. Обнаруженный разрыв (20.5% команд без двойника) объявляется числом, а не закрывается молча.
