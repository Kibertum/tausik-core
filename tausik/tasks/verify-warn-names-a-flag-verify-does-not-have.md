## Goal

`tausik verify --task <slug>` при пустой области печатает: «WARN: no relevant_files passed — scoped gates SKIPPED. v1.3 removed full-suite fallback. Pass --relevant-files for verification.» У самой команды `verify` флага `--relevant-files` НЕТ (project_parser_verify.py: только --task, --scope, --no-tests-expected). Сообщение предписывает действие, невыполнимое той командой, которая его напечатала — класс уже закрытой block-messages-phantom-go-and-platform и конвенции #282.  ВАЖНО (установлено экспериментом, а не чтением кода): рабочий путь СУЩЕСТВУЕТ и он третий — `tausik task update <slug> --relevant-files ...`, после чего `verify --task` становится scoped и pytest реально исполняется. То есть чинить надо не механизм, а УКАЗАТЕЛЬ: сообщение называет флаг несуществующей команды вместо существующей. Это удешевляет задачу и меняет предпочтительный вариант.  Замер на powershell-tool-bypasses-bash-firewall: - run #1267 и #1269, область пуста: [PASS] hadolint, [SKIP] pytest, Duration 0 ms, чек ПОДПИСАН, exit=0. - run #1270 после `task update --relevant-files`: [PASS] pytest, Duration 8516 ms. Разница — одна команда, о которой сообщение молчит.  Второй, отдельный симптом той же слепоты: `task done --ac-verified --relevant-files ...` падает на гейте verify-first ДО того, как сохранит relevant_files, поэтому флаг у task done не помогает выйти из состояния «область пуста». Цепочка из CLAUDE.md («verify --task, затем task done читает кэш») для такой задачи неисполнима буквально, пока не вызван task update.  Ретро от 2026-05-02 (docs/ru/research/tausik-1.4-composer-retro) называло закрытия с «no relevant_files passed — scoped gates SKIPPED» главным системным риском батча. Механизм тот же спустя год, а единственная подсказка ведёт в тупик — что делает игнорирование предупреждения рациональным поведением, а не небрежностью.  Варианты: (а) переписать сообщение на `tausik task update <slug> --relevant-files ...` — минимальная честная правка; (б) дать verify собственный --relevant-files, чтобы цепочка CLAUDE.md работала как написана; (в) брать область из git diff рабочего дерева. Молчаливое «оставить как есть» запрещено.

## Acceptance Criteria

1. Указатель честен: ни одно сообщение о пустой области больше не называет флаг команды, у которой его нет. Проверено ТЕСТОМ, который берёт текст предупреждения, вытаскивает из него предлагаемую команду с флагами и сверяет флаги с реальным парсером argparse — а не сравнивает строку с ожидаемой строкой. Покрыты оба места: verify_cached_run.py (WARN при пустой области) и gate_runner.py (skip_reason при отсутствии relevant_files).
2. Цепочка из CLAUDE.md («verify --task, затем task done читает кэш») исполнима БУКВАЛЬНО: у verify появляется собственный --relevant-files. Он ОБЪЯВЛЯЕТ область (сохраняет её в задачу — один источник правды, тот же, что читает task done) и затем проверяет. Без --task флаг отвергается внятной ошибкой, а не тихо игнорируется.
3. Догфуд на живой задаче: verify --task <slug> --relevant-files <файлы> даёт [PASS] pytest с ненулевым Duration и подписанный чек, а последующий task done читает КЭШ (cache hit), а не гоняет гейты заново. Приведены номера прогонов.
4. Второй симптом той же слепоты закрыт: task done --ac-verified --relevant-files ... больше не падает на verify-first ДО сохранения области. Объявленная область записывается в задачу до запуска гейта закрытия, поэтому повторный вызов (или verify) уже видит её. Проверено тестом на реальном task_done: первый вызов падает на verify-first, но relevant_files в задаче УЖЕ сохранены.
5. НЕГАТИВНЫЕ И ГРАНИЧНЫЕ СЦЕНАРИИ (каждый — тест): --relevant-files без --task -> явная ошибка с ненулевым кодом; --relevant-files с пустым списком не стирает уже объявленную область молча; несуществующий путь в списке не превращает verify в зелёный (гейт всё равно скипается и это видно); задача без единого сопоставленного теста по-прежнему НЕ закрывается зелёной (поведение verify_no_test_mapped не ослаблено); сохранение области при провалившемся task done НЕ переводит задачу в done и не портит другие поля.
