## Goal

НАЙДЕНО СВЕРКОЙ SENAR 9.5 В #202, ИЗМЕРЕНО ПРОГОНОМ ЧЕРЕЗ РЕАЛЬНЫЙ ХУК, А НЕ ЧТЕНИЕМ КОДА. Дефект задачи write-gate-parses-command-text-not-writes, закрытой в #201: она закрыла ЗАМЕРЕННУЮ форму python скрипт.py и оставила соседние, отличающиеся одним токеном.

ЗАМЕРЫ. python h2.py даёт exit 2 BLOCKED. python h2.py -m foo даёт exit 0 ALLOWED — та же запись, тот же скрипт. python h2.py --mode -c тоже ALLOWED. python3.11 h2.py, python3.12 h2.py, pythonw h2.py, py -3 h2.py — все ALLOWED.

ДВЕ КОРНЕВЫЕ ПРИЧИНЫ, И ОНИ ОДНОГО КЛАССА. (1) В bash_write_parse.py проверка any(a in _NO_SCRIPT_FLAGS for a in args) сканирует ВСЕ аргументы, а не только идущие ДО первого позиционного. Флаг -c есть самый обычный флаг питоновской программы, то есть защита снимается не только злым умыслом, но и повседневной командой. (2) _PYTHON_NAMES содержит python, python2, python3, py, но _script_file_writes достижим только за проверкой _mentions_interpreter, а _INTERPRETERS в bash_cmd_scan.py знает лишь python и python3. Значит py и python2 суть МЁРТВЫЕ ВЕТВИ: константа заявляет покрытие, которого вызывающий не допускает. Версионных имён нет ни в одном из двух множеств, а python3.11 есть штатный способ вызова на многих системах.

ПОЧЕМУ ОДНОЙ ЗАДАЧЕЙ, А НЕ ДВУМЯ. По решению #296 граница идёт по КЛАССУ дефекта: здесь он один — гейт закрыл форму, которую замерил, и не проверил соседние формы той же команды. Обе причины живут в разборе аргументов одной команды и чинятся согласованно; разведение по задачам заставило бы дважды доказывать одно и то же утверждение о покрытии.

ОТЯГЧАЮЩЕЕ. Тот же #201 записал правило #495 про объявленный остаток, который называет неверный разрез, и переписал абзац границы гейта — а новый абзац снова заявляет больше, чем гейт делает. Это второй заход на те же грабли в том же файле.

НАЧИНАТЬ С ЗАМЕРА, НЕ С ПОЧИНКИ. Первым делом параметризовать существующие тесты хука по множеству имён интерпретатора и по позиции флага, увидеть красное, и только потом трогать разбор. Проверить и обратную сторону: python tests/test_bash_write_gate_hook.py сейчас ЧИТАЕТСЯ и даёт фантомные цели записи из литералов в тестовом файле — то есть возможен и ложный БЛОК, а не только пропуск.

## Acceptance Criteria

AC1. ЗАМЕР ДО ПОЧИНКИ. Существующие тесты хука параметризованы по МНОЖЕСТВУ имён интерпретатора (python, python3, python3.11, python3.12, python2, pythonw, py, py -3, python.exe) и по ПОЗИЦИИ флага (-m/-c после позиционного скрипта). Красное зафиксировано в журнале задачи ДО правки разбора, с перечнем прошедших мимо форм.

AC2. ПРОПУСК ЗАКРЫТ. Для КАЖДОЙ формы из AC1 команда, чей скрипт пишет вне scope_paths активной задачи, даёт exit 2 через РЕАЛЬНЫЙ хук (subprocess, не юнит на парсере), и stderr называет путь записи. Проверено прогоном.

AC3. ЗЕЛЁНАЯ ВЕТВЬ ИЗМЕРЕНА, А НЕ ОБЪЯВЛЕНА. Для КАЖДОЙ формы из AC1 та же команда со скриптом, пишущим ВНУТРИ scope_paths, даёт exit 0. Единственное отличие от AC2 — путь записи, поэтому гейт, блокирующий любой `python <script>`, здесь падает (память #491).

AC4. ЛОЖНЫЙ БЛОК НЕ ЗАВЕДЁН. `python -m pytest tests/test_x.py` остаётся exit 0, включая склеенные и кластерные формы `-mpytest` и `-um pytest`: флаг, стоящий В ПОЗИЦИИ ОПЦИИ (до первого позиционного), по-прежнему означает «скрипта нет». Проверено прогоном обеих форм.

AC5. МЁРТВАЯ ВЕТВЬ ЛИКВИДИРОВАНА ИЗМЕРЕНИЕМ, А НЕ ОБЪЯВЛЕНИЕМ. Достижимость каждого имени из множества имён Python-интерпретатора доказана тестом, который краснеет при удалении имени; ни одно имя не остаётся недостижимым из-за постороннего условия. Множество имён ВЫВЕДЕНО (versioned-форма распознаётся правилом), а не перечислено литеральным списком, который снова разойдётся со стандартной формой вызова.

AC6. МУТАЦИЯ С НОРМАТИВНЫМ ОСНОВАНИЕМ (#500). Для каждой красной ветви названо, ЧТО именно она предотвращает (запись мимо ACL активной задачи, SENAR Rule 2 / QG-0), и мутация делается на ЦЕЛЕВОЙ строке разбора: снятие починки возвращает ALLOWED ровно на форме, ради которой правка сделана. У каждой мутации отдельным утверждением проверена СОСТОЯВШАЯСЯ настройка (#496) до чтения измерителя.

AC7. ОБРАТНАЯ СТОРОНА ЗАМЕРЕНА И ПРЕДЪЯВЛЕНА. Поведение `python tests/test_<x>.py` (прямой запуск тестового файла) измерено прогоном; если оно даёт фантомные цели записи и ложный БЛОК — исход зафиксирован цифрами и либо починен здесь, либо заведён отдельной задачей со ссылкой на замер. Молчаливого «наверное, нормально» нет.

AC8. ОБЪЯВЛЕННАЯ ГРАНИЦА СОВПАДАЕТ С ИЗМЕРЕННОЙ (#495). Абзац остаточной границы в docs/ru/enforcement-coverage.md и докстринг _script_file_writes перечитаны и приведены в соответствие с ФАКТИЧЕСКИМ разрезом после починки; ни одно предложение не заявляет покрытия шире измеренного.

AC9. РАЗВЁРНУТАЯ КОПИЯ ОБНОВЛЕНА (#499). После правки scripts/ прогнан bootstrap.py --ide all, и совпадение scripts/hooks/*.py с развёрнутой копией .claude/scripts/hooks/*.py проверено сравнением.

AC10. ГЕЙТЫ ЗЕЛЁНЫЕ. Полная лента pytest без failed/errors (задача трогает тестовый файл — #478), mypy без ошибок, ruff чистый на затронутых файлах.

AC11. ПОВЕРХНОСТЬ УГРОЗЫ НАЗВАНА И ИЗМЕРЕНА (security). Гейт есть контроль ДОСТУПА: он держит ACL записи активной задачи (SENAR Rule 2) и запрет записи без задачи (QG-0). Модель нарушителя здесь — НЕ злой умысел, а повседневная команда: `-c` есть обычный флаг прикладной программы, а `python3.11` есть штатный способ вызова, поэтому защита снималась без всякого обхода. Утверждение о поверхности проверяется прогоном обоих правил на КАЖДОЙ форме из AC1: (а) активная задача со scope_paths — запись вне ACL даёт exit 2 с упоминанием SENAR Rule 2; (б) активной задачи нет — та же запись даёт exit 2 с «No active task». Ни одна форма не остаётся непроверенной хотя бы по одному из двух правил. Расширение не создаёт НОВОЙ поверхности: разбор остаётся чтением файла-скрипта в пределах дерева проекта с прежними ограничителями (размер, fail-soft на нечитаемом файле), новых исполнений кода не вводится.
