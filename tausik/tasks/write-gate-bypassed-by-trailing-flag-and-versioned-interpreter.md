## Goal

НАЙДЕНО СВЕРКОЙ SENAR 9.5 В #202, ИЗМЕРЕНО ПРОГОНОМ ЧЕРЕЗ РЕАЛЬНЫЙ ХУК, А НЕ ЧТЕНИЕМ КОДА. Дефект задачи write-gate-parses-command-text-not-writes, закрытой в #201: она закрыла ЗАМЕРЕННУЮ форму python скрипт.py и оставила соседние, отличающиеся одним токеном.

ЗАМЕРЫ. python h2.py даёт exit 2 BLOCKED. python h2.py -m foo даёт exit 0 ALLOWED — та же запись, тот же скрипт. python h2.py --mode -c тоже ALLOWED. python3.11 h2.py, python3.12 h2.py, pythonw h2.py, py -3 h2.py — все ALLOWED.

ДВЕ КОРНЕВЫЕ ПРИЧИНЫ, И ОНИ ОДНОГО КЛАССА. (1) В bash_write_parse.py проверка any(a in _NO_SCRIPT_FLAGS for a in args) сканирует ВСЕ аргументы, а не только идущие ДО первого позиционного. Флаг -c есть самый обычный флаг питоновской программы, то есть защита снимается не только злым умыслом, но и повседневной командой. (2) _PYTHON_NAMES содержит python, python2, python3, py, но _script_file_writes достижим только за проверкой _mentions_interpreter, а _INTERPRETERS в bash_cmd_scan.py знает лишь python и python3. Значит py и python2 суть МЁРТВЫЕ ВЕТВИ: константа заявляет покрытие, которого вызывающий не допускает. Версионных имён нет ни в одном из двух множеств, а python3.11 есть штатный способ вызова на многих системах.

ПОЧЕМУ ОДНОЙ ЗАДАЧЕЙ, А НЕ ДВУМЯ. По решению #296 граница идёт по КЛАССУ дефекта: здесь он один — гейт закрыл форму, которую замерил, и не проверил соседние формы той же команды. Обе причины живут в разборе аргументов одной команды и чинятся согласованно; разведение по задачам заставило бы дважды доказывать одно и то же утверждение о покрытии.

ОТЯГЧАЮЩЕЕ. Тот же #201 записал правило #495 про объявленный остаток, который называет неверный разрез, и переписал абзац границы гейта — а новый абзац снова заявляет больше, чем гейт делает. Это второй заход на те же грабли в том же файле.

НАЧИНАТЬ С ЗАМЕРА, НЕ С ПОЧИНКИ. Первым делом параметризовать существующие тесты хука по множеству имён интерпретатора и по позиции флага, увидеть красное, и только потом трогать разбор. Проверить и обратную сторону: python tests/test_bash_write_gate_hook.py сейчас ЧИТАЕТСЯ и даёт фантомные цели записи из литералов в тестовом файле — то есть возможен и ложный БЛОК, а не только пропуск.
