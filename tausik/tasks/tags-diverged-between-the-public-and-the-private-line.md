## Goal

ЗАМЕР ПОСЛЕ ПУБЛИКАЦИИ, сессия #181. Публикация тегов не касалась и не могла: push нёс одну ссылку ветки, и проверка tags_unmoved это подтвердила. Но когда линии сошлись, расхождение стало видимым.

Локально 22 тега, на GitHub 9. Одноимённые указывают на РАЗНОЕ: v1.8.0 локально 3866702f, на GitHub 623fb4e; v1.7.0 на GitHub отсутствует вовсе. git fetch --tags отказывается их перетирать словами «would clobber existing tag» — и отказывается правильно: молчаливая перезапись тега есть перемещение пина у чужого потребителя.

ПРОИСХОЖДЕНИЕ ИЗМЕРЕНО, А НЕ ПРЕДПОЛОЖЕНО: публичные теги ставились на ORPHAN-снимке, у которого не было общего предка с настоящей историей (замер сессии #178: github/main 13 коммитов, origin/main 405, merge-base пуст). Один и тот же номер релиза на двух линиях называет два разных дерева. README при этом велит подключать репозиторий сабмодулем, а сабмодуль пинится SHA или тегом.

ГЛАВНЫЙ ВОПРОС, КОТОРЫЙ ЗАДАЧА ОБЯЗАНА ЗАДАТЬ ДО ЛЮБОЙ РАБОТЫ: тег есть ОБЕЩАНИЕ ПОТРЕБИТЕЛЮ или внутренняя закладка? Если первое — публичные теги двигать нельзя никогда, и тринадцать недостающих ставятся новыми номерами на новой линии. Если второе — их можно привести к локальным, но всякий, кто уже спинился, поедет на другое дерево молча. Оба ответа необратимы по-разному, поэтому решать молча нельзя.

НЕГАТИВНЫЙ СЦЕНАРИЙ, обязательный: что бы ни решили, должно быть ДОКАЗАНО, что ни один существующий публичный тег не сменил объект — сравнением снимков ls-remote до и после, а не намерением. Функция tags_unmoved в scripts/publication_scope.py уже написана и работает на паре снимков; ей нужен только удалённый источник вместо локального.
