## Goal

НАЙДЕНО ЖИВЬЁМ В #199. Ошибочный вызов `tausik task add` печатает подсказку, которая САМА НЕВЕРНА, и следование ей даёт вторую ошибку.

ЧТО ПЕЧАТАЕТСЯ ПРИ ОШИБКЕ:
  examples:
    tausik task add <story-slug> <task-slug> "Title" --stack python --complexity medium --role developer
То есть три ПОЗИЦИОННЫХ аргумента.

ЧТО НА САМОМ ДЕЛЕ (tausik task add --help):
  usage: tausik task add [-h] [--story STORY_SLUG] [--slug SLUG] ... title
То есть ОДИН позиционный (title), а story и slug — ИМЕНОВАННЫЕ опции.

ЦЕНА ЗАМЕРЕНА, НЕ ПРЕДПОЛОЖЕНА: агент, следуя подсказке, получил ту же ошибку ВТОРОЙ раз подряд и разобрался только через --help. Подсказка не сокращает путь к исправлению, а удлиняет его — она хуже, чем отсутствие подсказки, потому что выглядит авторитетной.

ПОЧЕМУ ЭТО НЕ ОПЕЧАТКА В ТЕКСТЕ. Проект держит правило «не угадывай аргументы CLI — читай --help или docs/ru/cli.md». Подсказка на ошибке — ровно тот канал, которым правило и исполняется. Неверная подсказка подрывает механизм, а не строку.

ЧТО ПРОВЕРИТЬ ЗАОДНО (не предполагать — прогнать): совпадают ли примеры в блоках `examples:` ОСТАЛЬНЫХ подкоманд с их реальными сигнатурами. Дешёвый способ — сравнить машиной текст примера с argparse-сигнатурой для каждой подкоманды; несовпадение позиционных/именованных ловится автоматически. Это же даёт контроль, чтобы не разъехалось снова.

## Acceptance Criteria

AC-1 (конкретная ложь устранена): пример для `tausik task add` в scripts/project_parser_errors.py::EXAMPLES соответствует настоящей сигнатуре — ОДИН позиционный (title), story и slug именованными опциями. Сегодня там три позиционных.

AC-2 (проверяется КАЖДЫЙ пример, а не только починенный): добавлен тест, который берёт КАЖДУЮ строку реестра EXAMPLES, разбирает её shlex и подаёт НАСТОЯЩЕМУ парсеру TAUSIK. Пример, который парсер отвергает, роняет тест с именем этого примера. Реестр перестаёт быть текстом и становится проверяемым утверждением.

AC-3 (НЕГАТИВНЫЙ СЦЕНАРИЙ — контроль обязан краснеть): в реестр временно подкладывается заведомо неверный пример (лишний позиционный аргумент у команды, которая его не принимает) — тест ОБЯЗАН покраснеть и НАЗВАТЬ этот пример. Без этой ветви «все примеры валидны» неотличимо от теста, который ничего не парсит.

AC-4 (НЕГАТИВНАЯ ВЕТВЬ ОХРАНЫ ПУСТОГО ПРОГОНА): тест обязан падать, если реестр пуст или разобрано НОЛЬ примеров. Пустой прогон даёт зелёное по той же причине, что и здоровый, и это единственный способ их различить.

AC-5 (граничный случай — примеры-НАБРОСКИ): часть записей реестра является не вызовом, а наброском сигнатуры (например строка с {context,convention,dead_end,gotcha,pattern} — перечисление допустимых значений, а не значение). Такая строка НЕ парсится по построению. Решение принимается явно и записывается: либо набросок приводится к настоящему вызову, либо реестр получает способ пометить строку наброском и тест её пропускает — молчаливое исключение запрещено.

AC-6 (регрессий нет): полная лента (задача ДОБАВЛЯЕТ тестовый файл — память #478), mypy, verify.
