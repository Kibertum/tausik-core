## Goal

ДЕФЕКТ ЦЕЛОСТНОСТИ, найден аудитом цепочки поставки (сессия #117), подтверждён чтением кода лично.

ФАКТ: bootstrap_vendor._write_lock (:40-54) сохраняет в .lock поле sha = sha256(tarball) после каждой синхронизации. sync_deps (:283) при решении «качать или нет» сравнивает ТОЛЬКО lock.get("ref") == ref. Записанный дайджест не читается ни здесь, ни где-либо ещё — это write-only данные, создающие видимость lock-файла без единой гарантии, которую lock-файл обычно даёт.

ТОЧНАЯ ГРАНИЦА УГРОЗЫ (уточнено против первичной формулировки аудита): при ref=main и существующем .lock ветка :283-285 возвращает up-to-date и НЕ качает вообще, пока не передан force. Значит опасен именно путь bootstrap --update-deps, который форсит перекачку: он тянет текущее состояние мутабельной ветки и не сверяет результат ни с чем. Четыре из пяти внешних скиллов в skills.json закреплены за ref=main (проверено), то есть за содержимым чужой ветки на момент скачивания.

ПОЧЕМУ ЭТО НЕ «ПРОСТО ДОБАВИТЬ ПРОВЕРКУ»: сегодня у механизма нет места, где можно объявить ОЖИДАЕМЫЙ дайджест. Записанный sha фиксирует «что скачалось», а не «что должно было скачаться», поэтому сверять его с самим собой бессмысленно. Нужна декларация ожидания в skills.json — иначе проверка будет тавтологией.

ГРАНИЦА ЗАДАЧИ: реализуется МЕХАНИЗМ проверки и громкий сигнал о мутабельном ref. Фактические значения пинов (какие теги существуют у пяти внешних репозиториев) требуют сетевой сверки с первоисточником и в этой задаче НЕ выставляются — угадывать теги нельзя, неверный пин ломает bootstrap всем. Это отдельный шаг, выполняемый при наличии сети.

## Acceptance Criteria

1. Спецификация внешнего скилла в skills.json принимает необязательное поле sha256 — ОЖИДАЕМЫЙ дайджест тарбола. Отсутствие поля не ломает существующие записи (обратная совместимость сохранена).
2. Когда sha256 объявлен, sync_deps сверяет sha256 скачанного тарбола с ним ДО распаковки. Несовпадение — жёсткий отказ по этому скиллу (status=error с внятным текстом), распаковка не происходит, ни один файл не пишется. Fail-closed по конвенции #221.
3. Когда sha256 НЕ объявлен, а ref указывает на мутабельную ветку (не тег и не 40-символьный hex), в вывод идёт явное предупреждение с названием репозитория и указанием, чем это опасно. Молчания быть не должно — конвенция #226: неизвестность сообщается.
4. Записанный в .lock sha перестаёт быть write-only: при форсированной пересинхронизации, если новый дайджест отличается от лежащего в .lock, факт смены содержимого сообщается в результате (ключ sha_changed + прежний и новый дайджест). Пользователь узнаёт, что чужая ветка поехала под ним.
5. Существующее поведение кэша не сломано: lock с совпадающим ref и без force по-прежнему даёт up-to-date без сети.
6. Тесты (сеть не требуется, загрузка мокается):
   а) объявленный sha256 совпал — синхронизация проходит, файлы на месте;
   б) объявленный sha256 не совпал — status=error, каталог назначения НЕ создан/не изменён;
   в) sha256 не объявлен, ref=main — предупреждение выдано, синхронизация проходит;
   г) sha256 не объявлен, ref=v1.2.3 — предупреждения нет;
   д) форс-пересинхронизация с изменившимся содержимым — sha_changed присутствует в результате;
   е) регрессия: lock с тем же ref и без force возвращает up-to-date и в сеть не ходит.
7. Полный прогон pytest зелёный, гейт 400 строк не нарушен.
8. Документация: docs/ru/vendor-skills.md и docs/en/vendor-skills.md описывают поле sha256 и поведение при мутабельном ref — обе локали правятся вместе (гейта на translation drift нет, машина расхождение не поймает).

## Plan

## Rollback

git revert коммита. Изменение аддитивное и обратно совместимое: новое поле sha256 необязательно, при его отсутствии поведение отличается только появлением предупреждения. Данных не мигрируем, формат .lock расширяется только на чтение существующего поля. Откат восстанавливает текущее (непроверяющее) поведение и ничего не ломает. Точечный откат при ложных срабатываниях — снять жёсткий отказ в п.2, оставив предупреждения п.3 и п.4.
