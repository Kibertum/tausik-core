## Goal

ПРОТИВОРЕЧИЕ НАЗВАНО ВЛАДЕЛЬЦЕМ В СЕССИИ #188 И ПОДТВЕРЖДЕНО ЗАМЕРОМ. Решение github-stanovitsya-osnovnym-mestom-razrabotki-gitlab (2026-08-25) гласит: «GITHUB СТАНОВИТСЯ ОСНОВНЫМ МЕСТОМ РАЗРАБОТКИ, GITLAB — ЗЕРКАЛО И САЙТ». Фактически сессии #183-#188 вели разработку в GitLab: ветка v1-9-wave существует ТОЛЬКО на origin (GitLab), её upstream — origin/v1-9-wave, и восемь коммитов волн 1-2 плюс сегодняшний 64a242f уехали туда. На GitHub за это время лёг ОДИН публикационный коммит прямо в main (faaa10f, 2026-08-25 23:30).

ЗАМЕР, ОБЪЯСНЯЮЩИЙ, ПОЧЕМУ ЭТО НЕ ЧИНИТСЯ ОДНИМ PUSH:
  общий предок v1-9-wave и github/main — ОТСУТСТВУЕТ (git merge-base пуст);
  корни разные: v1-9-wave -> a158380, github/main -> f380a2e;
  коммитов в v1-9-wave, которых нет в github/main — 431.
То есть `git push github v1-9-wave` не догоняет публичную линию, а привозит в неё 431 коммит приватного архива — ровно ту историю, которую ЭТО ЖЕ решение оставляет приватной на GitLab, и в которой замер сессии #180 нашёл внутренний хост (17 файлов), имена четырёх чужих проектов (44 файла) и локальные пути с именем пользователя (12). Пуш ветки разработки на GitHub в нынешнем виде — утечка, а не синхронизация.

ТРЕТИЙ УЧАСТНИК ПРОТИВОРЕЧИЯ. Решения о механике выкладки (publish-the-github-public-mirror-via-a-fast-forward-child; poryadok-vykladki-zerkala-popravlen-dlya-vypuskov-s) описывают ИМЕННО зеркало: публикация идёт fast-forward-ребёнком поверх вычищенного orphan-корня, force запрещён файрволом, а 1.9 обязана лечь на main мержем release/1.9 либо squash-ом с Co-Authored-By автора PR #5 (иначе стирается авторство Okianiwa). Эта механика несовместима с «разработка живёт на GitHub»: нельзя одновременно вести ветки на публичной линии и держать её вычищенным orphan-корнем без общей истории.

ЧТО НАДО РЕШИТЬ ВЛАДЕЛЬЦУ (не выбирать в одиночку, варианты не равноценны):
  А. GitHub действительно основной: тогда нужен ПЕРЕЕЗД, а не push — новая линия разработки поверх github-корня, и правило, как в неё попадает приватный архив (никак? выборочно? одним снимком?).
  Б. Решение от 25.08 переформулировать по факту: разработка в GitLab, GitHub — публичная линия выпусков, и тогда «основное место разработки» из формулировки убрать, чтобы оно не читалось как невыполненное обещание.
  В. Гибрид с явным правилом: ветки разработки в GitLab, но КАЖДЫЙ выпуск обязан лечь на GitHub в срок X — тогда нужен механизм, а не память агента.

ДО КОДА ЗАМЕРИТЬ: (1) сколько выпусков 1.9 уже должно было лечь на GitHub и не легло; (2) содержит ли v1-9-wave те же четыре класса утечки, что нашёл #180, или они уже вычищены; (3) что именно ломается у потребителей, подключивших github.com/Kibertum/tausik-core сабмодулем, при каждом из трёх вариантов.

ЦЕНА МОЛЧАНИЯ УЖЕ ЗАПЛАЧЕНА: вопрос «пушить ли в GitHub» был задан в сессии #185, ответа не получил, и три последующие сессии продолжили пушить в GitLab по инерции — не потому, что так решили, а потому, что upstream ветки указывает туда. Решение, которое исполняется памятью агента, а не механизмом, не исполняется.
