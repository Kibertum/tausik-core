## Goal

Поиск по bootstrap/, harness/, scripts/ и docs/ даёт НОЛЬ упоминаний байтовых крышек (head -c, tail -c) и ноль правил о размере вывода команды. Строчные лимиты, которые агент выбирает сам, не защищают: одна длинная строка (минифицированный файл, JSON в одну строку, лог без переносов) переполняет контекст независимо от числа строк. Внешний источник, у которого этот приём измерен — github.com/Austin1serb/agents-md — называет его своим главным выигрышем и заявляет около -50% токенов на сопоставимых задачах; цифра ЧУЖАЯ и у нас не проверена, повторять её как свой результат нельзя (та же оговорка уже сделана про 65% caveman в комментарии к CAVEMAN_DIRECTIVE). Задача: ввести правило байтовой крышки для вывода неизвестного размера и назвать список команд, для которых безлимитный вызов запрещён (cat без диапазона, широкий rg, find, ls -R, git diff целиком). Проверить приёмом, который у нас уже принят для гейтов: правило проверяется мутацией, а не тем, что оно записано. Замер до и после — на нашем же наборе, а не пересказом чужого.

## Acceptance Criteria

ЗАМЕР СМЕНЫ #229 НА СОБСТВЕННОМ НАБОРЕ, ПРИБОРОМ ЭТОГО ЖЕ РЕЛИЗА. Рост контекста отнесён к инструменту, чей результат его вызвал (дельта до следующего вызова внутри одной смены и одного транскрипта): Bash даёт 11 883 280 токенов из 17 896 506 — 66.4% ВСЕГО роста, 9844 вызова, медиана 848, p90 2514, p99 6386, максимум 18 900. Write 8.9%, Edit 7.4%, Read 2.1%.

ЗАМЕР УТОЧНИЛ ПОСТАНОВКУ В ДВУХ МЕСТАХ. (1) Рост ШИРОКИЙ, а не хвостовой: верхний 1% вызовов Bash даёт лишь 6.8% роста Bash и 4.5% всего роста. Катастрофического единичного вывода в корпусе НЕ БЫЛО, потому что харнесс Claude Code сам режет вывод инструмента; на хосте без такой резки он бы был. (2) Правило НЕ пустое место: PostToolUse-хук tool_output_truncation_nudge существует и работает — но считает СТРОКИ с порогом 250, то есть ровно та слепота, которую называет постановка: одна длинная строка его не трогает.

AC1. У СУЩЕСТВУЮЩЕГО ХУКА ПОЯВЛЯЕТСЯ БАЙТОВЫЙ ПОРОГ РЯДОМ СО СТРОЧНЫМ. Новый хук не пишется — расширяется имеющийся. Порог настраивается тем же способом (config, затем переменная окружения, затем умолчание), умолчание обосновано замером, а не вкусом.
AC2. ОДНА ДЛИННАЯ СТРОКА СРАБАТЫВАЕТ. Тест: вывод из ОДНОЙ строки длиной сильно больше байтового порога даёт совет, хотя строчный порог не превышен. Это тот самый случай, ради которого задача заведена, и он проверяется прямо, а не через сумму.
AC3. СОВЕТ НАЗЫВАЕТ, КАКОЙ ИМЕННО ПОРОГ ПРЕВЫШЕН И ЧЕМ ЛЕЧИТЬ. Сообщение различает превышение по строкам и по байтам и в байтовом случае называет идиому крышки. Совет, не говорящий что делать, есть шум.
AC4. ПРАВИЛО ЗАПИСАНО И НАЗЫВАЕТ КОМАНДЫ ПОИМЁННО. В контракте агента перечислены вызовы, у которых размер вывода неизвестен заранее (cat без диапазона, широкий rg, find, ls -R, git diff целиком) и сказано, чем их ограничивать. Числа замера приведены со ссылкой на источник, ЧУЖАЯ цифра -50% не повторяется как своя.
AC5 (НЕГАТИВНЫЙ СЦЕНАРИЙ, ПРОВЕРКА МУТАЦИЕЙ). Правило проверяется тем, что оно СРАБАТЫВАЕТ, а не тем, что записано: вывод ниже обоих порогов совета НЕ даёт; вывод выше строчного, но ниже байтового даёт совет про строки; выше байтового, но ниже строчного — про байты; выше обоих — называет оба. Хук остаётся советующим: он НЕ меняет результат инструмента и НЕ блокирует вызов, и тест это утверждает. Испорченный stdin, отсутствующий tool_response и нечисловой порог не роняют хук.
AC6 (БЕЗОПАСНОСТЬ). Совет печатает ТОЛЬКО имена инструмента и числа. Тест: вывод инструмента, содержащий секрет, не приводит к попаданию этой подстроки в stderr — иначе хук, созданный экономить контекст, начал бы копировать содержимое в журнал.
