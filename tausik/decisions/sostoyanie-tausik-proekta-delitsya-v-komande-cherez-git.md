## Decision

Состояние TAUSIK-проекта делится в команде через git-native файлы В ВЕТКЕ (по файлу на сущность, md+frontmatter), НЕ через внешний стор (Notion/сервер). Git — канонический источник правды, БД — пересобираемый кэш. Два этажа: durable code-coupled стейт (задачи/план/логи/эпики/стори + решения/память) едет в git; живая координация «кто над чем сейчас, до мержа» ОТЛОЖЕНА и при необходимости решается git-ом (claimed_by+push), не сервером.

## Rationale

Сценарий владельца — два инженера на разных ветках связанного функционала, дополняют друг друга — по определению про версии/ветки/слияние, а это умеет только git. Внешний стор (Notion/Obsidian-vault/сервер) branch-agnostic: решение, принятое на feature-A, он показывает коллеге сразу, хотя кода X в его ветке нет; свернули feature-A — в сторе висит решение про несуществующий код. Это отказ, против которого построен TAUSIK (памятка #229: стейт, оторванный от кода, врёт про код). Git-native стейт-в-ветке сливается как код: решение приезжает в main ровно с кодом feature-A; стейт становится branch-aware даром (сейчас .tausik/ вне git и branch-blind). Obsidian — читатель поверх git-native md, не механизм синхронизации. Только git-canonical даёт реальное СЛИЯНИЕ правок двух людей; db-canonical дал бы лишь видимость+бэкап (последний экспорт затирает). Несущий риск — decisions/memory на локальных автоинкрементах (#171/#307) столкнутся на ветках, поэтому первым делом стабильная идентичность (state-git-stable-ids). Объём (tasks+logs+epics+stories+decisions+memory, без verification/sessions) — выбор владельца. Этаж 2 отложен: claimed_by+pull закрывает ~90% координации без сервера, а сервер нарушил бы zero-deps и ре-ввёл расцепку.
