## Decision

Подпись скилла остаётся подписью сырых байт; нормализация окончаний строк перед хешированием отвергнута. Платформозависимость лечится там, где байтам позволено дрейфовать: (1) ядро клонирует вендор-репу с отключённой конверсией — git -c core.autocrlf=false -c core.eol=lf clone, плюс git config core.autocrlf false в клоне ради последующих pull; (2) skill sign отказывается подписывать сконвертированное дерево — расхождение i/ и w/ в 'git ls-files --eol'. Плюс .gitattributes '* -text' в шаблоне и spec.

## Rationale

Нормализация ломает то, ради чего подпись существует. Скилл — исполняемое содержимое (хуки, .py, .sh); подпись, слепая к окончаниям строк, перестаёт покрывать свойство, которое меняет поведение: '#!/bin/sh\r' даёт 'bad interpreter'. Она же требует классификатора text/binary ВНУТРИ границы доверия, а на классификатор влияет содержимое файла, то есть атакующий. И поле size в манифесте пришлось бы либо выкинуть, либо тоже нормализовать. Ключевое наблюдение: 'git clone --depth 1' в clone_repo (scripts/skill_manager.py:122) — команда ЯДРА, а не издателя, и она наследует core.autocrlf потребителя. Значит потребительскую половину ядро закрывает у себя, не полагаясь на .gitattributes в чужом репозитории, которого там может не быть. Репро: скилл, подписанный по LF, без .gitattributes — клон с autocrlf=true даёт другой sha256 и size 32 вместо 28 -> 'Install refused — modified: SKILL.md'; клон с autocrlf=false и клон с '-c core.autocrlf=false -c core.eol=lf' -> VALID. Одного (1) мало: издатель, подписывающий из CRLF-дерева, всё равно выпустит манифест, не совпадающий с байтами репозитория, — отсюда (2). Проверено: 'git ls-files --eol' доступен и показывает 'i/lf w/lf attr/'.
