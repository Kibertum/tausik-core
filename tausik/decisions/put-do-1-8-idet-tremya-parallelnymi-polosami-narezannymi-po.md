## Decision

Путь до 1.8 идёт ТРЕМЯ ПАРАЛЛЕЛЬНЫМИ ПОЛОСАМИ, нарезанными по ТЕРРИТОРИИ ФАЙЛОВ, а не по темам: A — km-* и l26-memory-decay (слой памяти); B — kb-global-* (отдельная БД в папке пользователя); C — brainh-*, kb-brain-deprecate, kb-notion-publisher. Полоса D (kb-docs-*) сериализуется ПОСЛЕ слияния A+B+C — она финальный гейт по #161. Внутри полосы A параллелить запрещено.

## Rationale

Сессия #152. Субстрат появился в этой же сессии: до фикса state-export-trigger-misses-task-linked-decisions решение с task_slug и почти любая мутация задачи в git НЕ уезжали — параллельные ветки молча теряли состояние друг друга, а status расхождения не показывал. Теперь один файл на сущность, журнал append-only: разные задачи дают разные файлы и чистый merge. Резать по территории, а не по темам, потому что узкое место не задачи, а ТРИ ОБЩИХ ФАЙЛА: CHANGELOG.md/.ru.md (гейт требует запись от каждой задачи в общую шапку [Unreleased]), миграции (ассерт SCHEMA_VERSION == max(MIGRATIONS) ломается при двух полосах), docs/_generated/constants.json. A берёт диапазон миграций; B по своей цели проектной схемы не касается вообще (своя БД); C изолирована в brain_*. Внутри A последовательность задана решением #143 (шаги 2->3->4->5->6), каждый опирается на схему предыдущего — резать её значит покупать конфликты миграций ради иллюзии скорости.
