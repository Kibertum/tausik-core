Ревью по правилу «каждые 5 закрытых задач». Читал не пересказ, а собственный диф 7121600..HEAD по scripts/: 19 файлов, +1107/-152.

НАЙДЕНО ОДНО, И ЭТО МОЯ ЖЕ ПРАВКА. session_usage_record описывает один факт тремя операторами (UPSERT в session_usage_metrics, DELETE прежнего зеркала, INSERT нового), а SQLiteBackend._ex коммитит каждый немедленно вне явной транзакции. Падение между DELETE и INSERT теряет зеркало завершённой смены НАВСЕГДА — второго вызова record_to_db у неё не будет. А отчёт по моделям теперь читает именно зеркало, то есть расход такой смены молча выпадет. Честно: окно было и до моей правки (UPSERT, затем INSERT), добавленный DELETE его расширил, но не создал. Заведена задача session-usage-record-is-three-commits-not-one-transaction; механизм для починки уже есть — backend_transaction.transaction(), вкладывающийся SAVEPOINT в чужую транзакцию.

ЧЕТЫРЕ МЕСТА ПРОВЕРЕНЫ И ПОДТВЕРЖДЕНЫ ЗДОРОВЫМИ, ПЕРЕЧИСЛЯЮ ИМЕННО ПОТОМУ, ЧТО ПРОВЕРЯЛ:
1. Контракт исключительности срезов usage_events после моей перестановки цел: потасковый rollup берёт task_slug IS NOT NULL, корзина «вне задачи» — task_slug IS NULL AND source <> 'session_record', отчёт по моделям — source = 'session_record'. Три множества попарно не пересекаются, двойного счёта нет ни в одной паре.
2. _split в token_rows определяется внутри цикла по записи и замыкается на n этой же записи — переиспользования между сообщениями нет.
3. transcript_locator при первом файле с неподходящим cwd прерывает обход каталога, не проверяя остальные. Для каталога, все транскрипты которого от одного проекта, это верно; переименование каталога проекта дало бы пропуск. Оставлено сознательно: альтернатива — читать каждый файл каталога, а это десятки открытий на каждый запуск хука.
4. _cost_cell при cost_usd == 0.0 и токенах > 0 говорит «не измерено». Проверено, что настоящий ноль (ноль токенов) по-прежнему печатается как $0.0000, то есть измеренное отсутствие расхода отличается от неизмеренного.

ЧТО РЕВЬЮ НЕ СМОТРЕЛО, ЧТОБЫ НЕ СОЗДАВАТЬ ВПЕЧАТЛЕНИЯ ПОЛНОТЫ: поведение под параллельной нагрузкой (у него своя задача verify-endpoint-test-aborts-intermittently-under-parallel-load), производительность перестроения ленты на больших деревьях, и поведение на не-Windows хостах — весь замер смены снят на Windows.
