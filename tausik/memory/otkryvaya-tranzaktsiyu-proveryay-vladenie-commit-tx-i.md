begin_tx у SQLiteBackend внутри уже открытой транзакции НИЧЕГО НЕ ДЕЛАЕТ, а commit_tx и rollback_tx делают безусловно: зовут commit/rollback у связи и сбрасывают _in_tx. Поэтому функция, открывающая транзакцию БЕЗ проверки владения, при вызове изнутри чужой транзакции откатывает строки ВЫЗЫВАЮЩЕГО и возвращает ему закрытую транзакцию, которую тот считает своей. Исключения при этом нет: вызывающий видит только ту ошибку, которую ждал.

ЗАМЕР (#211): внешние begin_tx + epic_add, затем вложенный adapt_delta, отказавший по охране. Эпик ИСЧЕЗ, _in_tx стал False, ни одного сигнала о потере.

ПРАВИЛО. Пиши owns_tx = not self.be._in_tx; открывай только при owns_tx; commit_tx и rollback_tx зови ТОЛЬКО при owns_tx, иначе просто пробрасывай исключение. Образец в проекте есть — service_task._write_update_atomically, и его докстринг эту опасность называет.

И СЛЕДСТВИЕ, КОТОРОЕ НАДО ОБЪЯВЛЯТЬ ВСЛУХ: при чужой транзакции атомарность ДЕЛЕГИРУЕТСЯ вызывающему, то есть твоя гарантия «отказ есть не-событие» становится УСЛОВНОЙ. Отменить только свою часть можно было бы через SAVEPOINT, которого у бэкенда нет. Докстринг обязан называть условие; тест обязан проверять НАСТОЯЩИЙ контракт (строка записана, но откат вызывающего её убирает), а не желаемый.

ОБЩИЙ УРОК ШИРЕ ТРАНЗАКЦИЙ: берясь за примитив, снимай инвентарь его СУЩЕСТВУЮЩИХ применений — конвенция могла быть уже сформулирована рядом. В #211 приём owns_tx лежал в соседнем файле с докстрингом ровно про эту опасность, а я его не искал.
