ЗАМЕРЕНО В СЕССИИ #191, ВОСПРОИЗВЕДЕНО ДВАЖДЫ.

СИМПТОМ. `tausik verify --task <slug> --relevant-files ... tausik/tasks/<slug>.md` печатает хендл, а следующий за ним `task done --verify-handle` отвечает: «verify-handle: the files this receipt covers have changed since verify run #N (files_hash A -> B). This is the substantive refusal, not a cache miss». Повтор не помогает: хеш идёт дальше на каждом прогоне. Наблюдалось 870e9d910c7c -> edd0acd46e7b -> e8d9e08ecc20.

ПРИЧИНА. Сам прогон verify ПИШЕТ в задачу — объявленную область, номер прогона, квитанцию. Экспорт задачи tausik/tasks/<slug>.md от этого меняется. Если этот файл объявлен покрытым, квитанция протухает ровно в тот момент, когда её выписали. Условие невыполнимо в принципе, а не «не повезло со свежестью».

ЧТО ДЕЛАТЬ. Исключить из --relevant-files собственный экспорт задачи. Остальные файлы tausik/ (решения, память, ДРУГИЕ задачи) класть можно — их verify не трогает. Проверено: с семью файлами вместо восьми закрытие прошло с первого раза.

ГДЕ ЭТО КУСАЕТ ЧАЩЕ ВСЕГО. У задач, продукт которых есть ЗАПИСИ — разбор, вердикты, решения, планирование. Такая задача естественно объявляет областью свой экспорт и упирается в стену. Соблазн при этом — обвинить кэш и уйти в цикл verify/done.

КЛАСС ИЗВЕСТЕН: конвенция #424 не при чём, а вот [[#409]] — та же болезнь: проверка обязана вычитать из рабочего дерева бухгалтерию самого фреймворка. Здесь это не сделано в расчёте покрытия квитанции.

Задача: [[verify-handle-dies-on-a-tasks-own-export-file]]. Смежное: [[convention-verify-task-bez-relevant-files-ne-sertificiruet]] — без области квитанция не сертифицирует ничего, поэтому «просто не объявляй область» решением НЕ является.
