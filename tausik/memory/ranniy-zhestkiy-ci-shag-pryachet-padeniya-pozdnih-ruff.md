ИНЦИДЕНТ (v1.7.0, сессия #112): GitHub CI выглядел «отработавшим» и релиз выложили, но на самом деле CI был красным — и НЕ был зелёным никогда. .github/workflows/tests.yml гонит шаги по порядку, ruff check — ЖЁСТКИЙ (без || true) и РАНЬШЕ pytest. Оставленный мёртвый skip_tools дал ruff F841 → ruff падал первым → pytest на ВСЕЙ матрице не запускался. Когда починил ruff, pytest впервые доехал и вскрыл предсуществующую несовместимость с Python 3.13 (3 теста), которая пряталась за красным ruff неопределённо долго.

КЛАСС: ранний жёсткий шаг пайплайна маскирует всё, что за ним. «Зелёный по последнему прогону» ≠ «все шаги реально исполнялись». Одна ошибка прячет другую (ср. gotcha #205: addopts прячет slow-полосу — тот же класс, другой слой).

3.13-ПЕРВОПРИЧИНЫ (обе — правки ТЕСТОВ, не продукта):
1. Python 3.13 сменил ntpath.isabs: drive-relative путь БЕЗ буквы диска ('\\work\\proj', то что даёт os.path.normpath('/work/proj') на Windows) теперь non-absolute (был absolute на 3.11). Проверка: py -3.11 -c "os.path.isabs('\\\\work\\\\proj')"=True vs py -3.13=False. Тест-фикстуры, строящие пути через normpath('/x'), на 3.13 ломаются — якорить os.path.abspath (реальный project_dir всегда полностью абсолютный).
2. subprocess.run(text=True) строгий декод вывода: тест намеренно заставлял дочерний процесс писать битые cp1251-байты; на UTF-8 локали (Linux) + 3.13 строгий декод падал UnicodeDecodeError ИЗ subprocess.run (падал сам harness, не ассерт). Фикс: errors="replace".

УРОКИ ДЛЯ ПРОЦЕССА:
- Автор гоняет локально ОДНУ версию Python (3.11); CI — матрицу 3.11/3.12/3.13. Обязательно прогнать локально через py -3.13 (на машине есть) ПЕРЕД пушем — «зелёно у меня на 3.11» ≠ «зелёно на матрице».
- Всплывшие при этом ble001 ('No module named ruff' — ruff не стоит в py -3.13) и gen_doc_constants (test_count через pytest --collect-only зависит от окружения) — АРТЕФАКТЫ локального py -3.13, не CI. Проверять гипотезу «локальный шум»: дошёл ли ПРОШЛЫЙ CI до шага-жертвы (если doc-check прошёл в CI, значит чистый CI собирает тот же count).
- Порядок шагов в CI важен: жёсткий линт раньше тестов = линт может маскировать тестовые падения. Рассмотреть: не-жёсткий линт ИЛИ отдельные независимые job'ы (тесты не зависят от линта).
