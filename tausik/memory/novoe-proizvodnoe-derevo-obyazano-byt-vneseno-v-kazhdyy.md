Сессия #153, три независимых находки за один час, один корень. Дерево tausik/ (git-native проекция состояния, эпик team-state-in-git, релиз 1.8) — второе производное дерево проекта после renar/ и третье после docs/_generated/. Оно не внесено ни в один реестр, который уже знает про предшественников:

1. .gitattributes закрепляет `renar/** text eol=lf` и в комментарии называет причину дословно (LF-генератор + core.autocrlf=true => ложный дрейф --check на Windows). tausik/** не закреплено => на свежем клоне под Windows 2095 файлов станут CRLF, а check_tree читает с выключенной universal-newline трансляцией и считает это порчей. Гейт краснеет гарантированно. Задача tausik-tree-gitattributes-lf.
2. complexity_understatement._GENERATED_DIRS содержит только "docs/_generated/". Девять сгенерированных .md проекции засчитались поведенческими файлами, и ложное «COMPLEXITY UNDERSTATED» ушло в лог супервизии — ровно та порча калибровки, ради предотвращения которой модуль и написан. Задача complexity-proxy-counts-state-projection.
3. Каскад task->story->epic пишет в проецируемые таблицы четырьмя вызовами и не проецирует ни одним, хотя соседний миксин для тех же таблиц проецирует. Задача cascade-mutations-never-project-to-tree.

ПРИЗНАК, ПО КОТОРОМУ ЭТО ЛОВИТСЯ ЗАРАНЕЕ. Все три реестра — РУЧНЫЕ ПЕРЕЧНИ каталогов или методов. Ни один не выводится из источника, поэтому появление новой сущности их не двигает, а отсутствие записи ничем не сигнализируется. Симметрично конвенции #354 (гарантия даётся свойством, а не перечнем точек вызова) и #339 (перечень в прозе, дублирующий реестр, обязан выводиться из источника тестом).

ЧТО ДЕЛАТЬ ПРИ ВВОДЕ ЛЮБОГО НОВОГО ПРОИЗВОДНОГО ДЕРЕВА. До закрытия задачи, которая его вводит: найти grep-ом по репозиторию все места, где упомянуто ИМЯ предыдущего дерева (renar/, docs/_generated/), и для каждого ответить письменно — применимо или нет. Ответ «неприменимо» тоже записывать: он и есть доказательство, что место рассмотрено.

ЧЕМ ЭТО НАШЛОСЬ, для метода. Ни одна из трёх не найдена поиском дефектов. Первая — предупреждением git при обычном `state export`. Вторая — предупреждением самого гейта при закрытии. Третья — расхождением `state export --check` на один файл. То есть все три УЖЕ кричали в вывод, и мимо них проходили, потому что предупреждение не блокирует. Довод в пользу разбора каждого warning, а не только красного.
