Проверено через GitHub API 25 августа 2026, а не по обзорам:

- kuzudb/kuzu — АРХИВИРОВАН. 4026 звёзд, последний push 2025-10-10, C++. Компанию купил Apple, репозиторий закрыт. Это тот самый движок, чьи цифры (9 мс против 3-4 с у Neo4j на путевых запросах, разрыв 374x) цитируют все обзоры «графовая БД для памяти агента».
- indradb/indradb — не архивирован, но последний push 2025-08-16, то есть двенадцать месяцев тишины. 2459 звёзд, Rust. Из Python доступен только через gRPC к отдельному серверному процессу; встраивание в процесс есть только для Rust.
- LadybugDB/ladybug — живой форк Kuzu, 1644 звезды, push в день замера. Развивается ИМЕННО под память агента.

ПОЧЕМУ ЭТО ВАЖНО НАМ: стек TAUSIK — Python 3.11+ stdlib, БД SQLite+FTS5. Любой из трёх есть компилируемая внешняя зависимость, а IndraDB из Python — ещё и отдельный процесс. Но решающий довод не в этом, а в замере выше: движок с четырьмя тысячами звёзд закрылся за год после покупки. Слой памяти есть ядро продукта, и ставить его на такое основание значит принять риск, который дорожная карта уже назвала вслух, отказываясь догонять claude-mem.

ЧТО ИЗ ЭТОГО БЕРЁТСЯ: не движок, а ФОРМА ЗАПРОСА. Многошаговый обход выражается рекурсивным CTE, который SQLite умеет сам, без единой зависимости. Эпик artifact-graph уже принял это решение — задача ag-artifacts-and-edges-with-provenance кладёт артефакты и рёбра В ТУ ЖЕ БД.

Кандидаты годятся как ЭТАЛОН СРАВНЕНИЯ для гипотезы r-code-graph-versus-fts5-on-hidden-dependencies, у которой порог провала уже объявлен: не бьёт наш гибрид на нашем репозитории — не интегрируем.
