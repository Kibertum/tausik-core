sum_usage_tokens два релиза складывала usage.iterations с верхним уровнем, потому что её тест утверждал {"input_tokens":100, "iterations":[{"input_tokens":35}]} -> 135. Эту фикстуру НИКТО не сверял с настоящим ответом API. Реальность обратная: iterations — полный перечень оплаченных проходов, включая первый, а верхний уровень есть ВИД этого списка (равен ему при n=1, равен первой записи при n>1). Значит функция возвращала ровно двойную величину, и это дошло до tokens_input/tokens_output/cost_usd в session_usage_metrics, то есть до цифры, которую tausik metrics называет расходом проекта на LLM.

ПОЧЕМУ ТЕСТ БЫЛ ЗЕЛЁН: он проверял не поведение источника, а предположение автора о нём. Такой тест не может покраснеть никогда — он тавтологичен по построению. Замер на живом дереве, смена #227: 23 818 сообщений из 23 836 (99.92%) несут одну итерацию, посимвольно равную верхнему уровню; множитель завышения 1.9999.

ПРИЁМ: прежде чем писать фикстуру для ВНЕШНЕГО формата (ответ API, полезная нагрузка хука, чужой файл), снимай форму с настоящего экземпляра и клади в тест ИМЕННО ЕЁ, с числами оттуда. И заводи отдельный тест, читающий живой источник и краснеющий, когда форма изменится — он пропускается, если источника нет, но именно он отличает «форма подтверждена» от «форма предположена».

ТОТ ЖЕ КЛАСС УЖЕ ВСТРЕЧАЛСЯ: цены моделей, месяцами считавшиеся по чужой ставке при зелёном тесте покрытия; сторож цен, следивший за маршрутизируемыми моделями вместо работающей. Общее у всех троих — проверялось НАЛИЧИЕ ИМЕНИ, а не ФАКТ (решение #335).
