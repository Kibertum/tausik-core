Хук разрешал интерпретатор цепочкой `[ -f "$PY" ] || PY=...`, заканчивающейся голым `python`. В Git Bash под Windows `python` в PATH нет вовсе, и каждая проверка, которой нужен Python, тихо деградировала.

Хуже того, `[ -f ]` отвечает не на тот вопрос и для ПУТИ: `C:/Python311/python.exe` существует как файл и при этом НЕ ЗАПУСКАЕТСЯ — MSYS ждёт форму `/c/Python311/python.exe` и отвечает «command not found». Обратная запись `C:\Python311\python.exe` не запускается тем более.

Единственный честный способ узнать, годится ли интерпретатор, — позвать его: `if "$cand" -c "" >/dev/null 2>&1; then PY="$cand"; fi`. Кандидаты: `$TAUSIK_PYTHON`, venv проекта, `python3`, `python`, `py`.

Соседние грабли того же вечера, все под Git Bash в Windows:

* `bash -c '<многострочный скрипт>'` теряет позиционные параметры ФУНКЦИЙ: `$1` внутри функции разворачивается в пустую строку. Git запускает хук файлом — проверять надо тоже файлом.
* Heredoc внутри подстановки команд, `X="$("$PY" - <<'EOF' … EOF)"`, отдаёт пустую строку молча. Заменяется на `-c` с многострочной строкой в одинарных кавычках.
* `subprocess.run(env=...)` не доносит переменные до Git Bash. Значение пишется в сам скрипт строкой `export VAR='...'`.
* Абсолютный путь скрипта вида `C:\...\tmp.sh` Git Bash открывает не всегда; скрипт кладётся в проверяемое дерево и запускается относительным именем.

Общий признак: тест или хук краснеет ПУСТЫМ ответом без сообщения об ошибке. Пустота под Windows почти всегда означает «путь или окружение не доехали», а не «условие не выполнилось».
