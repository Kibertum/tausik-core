Механизм, объявленный в N местах, разъезжается — и первым отваливается то место, о котором читатель не догадывается заглянуть. Гейт объявлялся в четырёх (метаданные, if/elif-диспетч, вывод «встроенности» из command is None, хардкод в task-done), и два QG-2 гейта жили ТОЛЬКО в четвёртом: не видны в gates status, не переключаемы, без строки в gate_runs — чек не мог доказать, что охрана закрытия отработала.

Правила, выведенные из gate-registry-single-source:

1. ФАЗА — часть объявления, а не место в коде. Гейты бывают двух сигнатур: scoped `(gate, files) -> (passed, output)` и post-scope «взять контекст закрытия и править отчёт». Держать их в одном реестре можно только если фаза объявлена и фильтруется на входе в раннер: иначе раннер вызовет чужую сигнатуру.

2. ЛЕНИВЫЙ АДРЕС РЕАЛИЗАЦИИ. impl как строка "module:function", резолв через importlib. Жадный импорт замыкает цикл (реестр -> гейт -> project_config -> реестр). Для гейтов, привязанных к сервису, — форма "svc:method" с getattr в момент вызова: раннее связывание молча ломает и переопределения подкласса, и тестовые шимы.

3. ОДИН ЧИТАТЕЛЬ ВКЛЮЧЁННОСТИ. Как только раннер начинает решать «звать ли гейт», он обязан спрашивать ТУ ЖЕ функцию, что и сам гейт. Иначе вопрос получает два ответа, которые расходятся в обе стороны: гейт числится включённым и не работает, либо наоборот. Я воспроизвёл этот дефект слоем ниже внутри задачи, которая его же и лечит, — поймал сьют.

4. ВЫКЛЮЧЕНИЕ ≠ БАЙПАС. Телеметрию байпаса слать только когда выключили гейт, который шипится ВКЛючённым. Opt-in гейт, который проект не принял, байпасом не является — иначе событие на каждом закрытии каждого проекта хоронит настоящие байпасы.

5. «Встроенность» — объявленный факт, а не вывод из формы конфига. command is None было верно для тогдашних встроенных гейтов по совпадению; ruff есть в реестре И является командным.
