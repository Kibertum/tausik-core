СИМПТОМЫ (сессия #111, релиз 1.7.0): bootstrap.py «сам» откатывался — один раз до состояния HEAD/v1.6.1 с потерей ВСЕЙ ветки OpenCode; git status показывал файл то чистым, то грязным; размер скакал 13935↔13522; моя же integrity-проверка падала, а через секунду grep говорил «всё на месте». Выглядело как мистика или порча ФС.

ПРИЧИНА: мои ревью-агенты. В задании было «RUN things», «reproduce», «construct the exact broken input and confirm the assertion fires». У tausik-reviewer и workflow-агентов есть Bash. Они добросовестно ломали строку в ЖИВОМ файле, проверяли красноту и возвращали назад. Один агент не успел вернуть — дерево осталось сломанным. Пять агентов делали это параллельно, пока я в том же дереве правил код и гонял тесты.

ПОСЛЕДСТВИЕ ХУЖЕ САМОЙ ПОРЧИ: все прогоны тестов, шедшие ОДНОВРЕМЕННО с ревью, недостоверны — их зелёный цвет ничего не доказывает, потому что дерево под ними менялось. Пришлось перегонять на тихом дереве (4716 FULL / 4583 FAST — первый достоверный).

ПРАВИЛА:
1. Ревью-агенту, которому разрешено RUN/reproduce, давать isolation:"worktree" — тогда «сломай и проверь» безопасно. Живое дерево — НИКОГДА, если сам в нём работаешь.
2. Перед тем как поверить «зелёному» прогону — убедиться, что нет параллельных мутирующих агентов. Прогон + ревью одновременно = бессмысленный прогон.
3. Integrity-проверка (каждое заявление CHANGELOG → grep по коду) ловит этот класс, а тесты — нет: тесты бы просто упали, и падение легко списать на что угодно. Держать такую проверку перед релизом.
4. Если проверка целостности противоречит grep'у — не списывать на ложную тревогу. Обе правы, просто в РАЗНЫЕ моменты: файл меняется между командами.
