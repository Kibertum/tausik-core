СЛУЧИЛОСЬ В СЕССИИ #120, дважды в одной задаче, и второй раз со мной же.

Разведочный скрипт искал определения таблиц шаблоном вида CREATE TABLE (\w+)\s*\((.*?)\)\s*; с DOTALL. Он доложил «расхождений фикстур со схемой нет». Обобщённый гейт, сверяющий ПО БАЛАНСУ СКОБОК, немедленно нашёл семь. Разведка ошиблась на 7 из 7.

ПРИЧИНА: определения колонок содержат вложенные скобки — CHECK(scope IN ('a','b')), DEFAULT (...), NUMERIC(10,2). Нежадный (.*?) закрывается на ПЕРВОЙ же ) внутри CHECK, поэтому «тело таблицы» получается обрезанным, а сравнение с каноном — бессмысленным. Хуже того, жадный вариант перескакивает через несколько CREATE TABLE и склеивает их в один, давая абсурдные цифры вроде «56 колонок против канонных 18».

ПРАВИЛО: структуру SQL разбирай СЧЁТЧИКОМ ГЛУБИНЫ СКОБОК, а не регуляркой. Готовая реализация — tests/test_ddl_fixture_parity.py::_iter_ddl_blocks, бери оттуда.

ОТДЕЛЬНЫЙ УРОК, ВАЖНЕЕ ТЕХНИЧЕСКОГО: я САМ написал в коде гейта комментарий про эту ловушку и всё равно оставил в журнале задачи вывод, полученный сломанным инструментом. Знать про ловушку и применить это знание — разные события. Если инструмент разведки и инструмент проверки разные, вывод разведки — гипотеза; доверяй проверке. Разведочный вывод «дефекта нет» вообще требует более сильного доказательства, чем «дефект есть»: второй самоподтверждается находкой, первый держится только на исправности инструмента.
