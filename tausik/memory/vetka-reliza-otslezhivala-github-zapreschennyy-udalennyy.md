НАЙДЕНО АУДИТОМ сессии #158. У ветки release/1.8-batch-s126 upstream был выставлен на github/release/1.8-batch-s126, тогда как память #352 прямо запрещает публикацию в github без явного разрешения владельца на КОНКРЕТНЫЙ push, а хэндофф сессии #154 гласит «пуш только в origin (GitLab)».

ПОЧЕМУ ЭТО КАПКАН, А НЕ НЕУДОБСТВО: голая команда git push отправляет в upstream. То есть правило существовало в памяти и в хэндоффе, а КОНФИГУРАЦИЯ РЕПОЗИТОРИЯ ему противоречила и делала запрещённое действие ДЕЙСТВИЕМ ПО УМОЛЧАНИЮ. Правило, которое надо помнить вопреки настройке, отказывает при первой же спешке — в этом проекте такой механизм («мы же помним») уже отказывал несколько раз.

ИСПРАВЛЕНО: git branch -u origin/release/1.8-batch-s126. Это локальная правка конфигурации, не публикация. Теперь умолчание безопасно, а не опасно.

ЗАМЕР НА МОМЕНТ НАХОДКИ: 26 коммитов впереди github, 16 впереди origin. То есть в github ветка отставала СИЛЬНЕЕ, и push «чтобы синхронизироваться» отправил бы туда 26 коммитов разом.

ОБЩЕЕ ПРАВИЛО, ШИРЕ ЭТОГО СЛУЧАЯ: если правило запрещает какое-то назначение, проверять НЕ ТОЛЬКО намерение агента, но и настройку, делающую это назначение умолчанием. Запрет в памяти и upstream в конфиге — разные слои, и они могут спорить молча. Проверять при аудите: git remote -v и upstream каждой рабочей ветки.

ОТДЕЛЬНО, НЕ ПОЧИНЕНО И ТРЕБУЕТ РЕШЕНИЯ ВЛАДЕЛЬЦА: 16 коммитов работы существуют ТОЛЬКО локально. Вся серия сессий #155-#158 — общая база знаний, отказ от авто-публикации, переезд каталога — не отправлена никуда. Это единственная точка отказа того же рода, против которой заводился бэкап самой базы знаний.
