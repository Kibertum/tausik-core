При импорте внешнего представления в БД вызов fm.get(key) схлопывает ДВА разных случая в None: «файл вообще не упоминал ключ» и «файл явно объявил пустое значение». Политика «источник побеждает» задумана для РАСХОЖДЕНИЯ значений, но в такой реализации применяется и к ОТСУТСТВИЮ — и устаревшая проекция молча делает UPDATE ... SET col=NULL, откатывая БД.

Различать обязательно: sentinel ABSENT для «ключа нет» (колонка целиком исключается из дельты — не сравнивается и не пишется) против ЯВНОГО пустого значения в духе "key: []" или "key: null" (легитимная очистка, источник побеждает).

Это ещё и сужение привилегии недоверенного ввода: дерево приходит из git pull, и после фикса оно не может обнулить колонку одним умолчанием — только явным значением.

Найдено на живых данных: 2 задачи, у которых файл не содержал relevant_files, а БД содержала список — sync обнулил бы их.
