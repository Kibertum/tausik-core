Миграции v52 и v56 в scripts/backend_migrations_v*.py прямо пишут в docstring: «FROZEN LITERAL, NOT AN IMPORT... importing the schema constants by reference would make a later edit retroactively change what this migration did -- the defect that backend_migrations_v52 had to be rewritten to remove».

В смене #228 я нарушил это правило в миграции 57: извлекал DDL таблицы из SCHEMA_SQL регулярным выражением и написал в комментарии, что «двум копиям не с чем разойтись». Рассуждение верное для обычного кода и НЕВЕРНОЕ для миграции. Миграция описывает ПРОШЛОЕ состояние схемы; чтение живой схемы означает, что добавленная завтра колонка задним числом изменит то, что миграция создавала вчера, и база, мигрировавшая до правки, разойдётся с базой, мигрировавшей после. Проект уже наступал на это и переписывал v52.

ПРАВИЛО: в файле миграции DDL — это КОПИЯ формы на момент версии, и она обязана нести объяснение, почему копия здесь правильна, а не небрежность. Общий принцип «не дублируй» тут не действует, потому что две сущности разные: схема есть текущее состояние, миграция есть исторический факт.

ВТОРОЙ УРОК, БОЛЕЕ ОБЩИЙ: прежде чем оправдывать нарушение принципа, посмотри, нет ли в этом же каталоге записанного исключения. Оно было — в трёх docstring подряд, — и я его не прочитал, потому что смотрел на код, а не на соседние файлы того же вида. Нашёл случайно, когда гейт размера файла заставил вынести миграцию в отдельный модуль по образцу соседей.

ТЕХНИЧЕСКАЯ ДЕТАЛЬ, РАДИ КОТОРОЙ DDL В МИГРАЦИИ ВООБЩЕ ПОНАДОБИЛСЯ: SQLite резолвит имена таблиц на этапе PREPARE, поэтому DELETE по отсутствующей таблице — жёсткая ошибка, а не пустая операция. Частичные фикстуры создают три-четыре таблицы и прыгают со старой версии сразу на голову, и чисто-данная миграция обязана это выдерживать: CREATE TABLE IF NOT EXISTS перед DELETE на настоящей базе не делает ничего, а в фикстуре обезвреживает DELETE.
