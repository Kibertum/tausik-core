Решение #283 назвало класс «файлы, которые между task start и verify пишет сам фреймворк» и перечислило его членов по одному найденному случаю — собственному экспорту задачи. Через две сессии живой прогон предъявил второго: task start переключает status: open -> active в проекции РОДИТЕЛЬСКОЙ истории (решение #286). Команда та же, файлов два.

ПОЧЕМУ ИНВЕНТАРЬ ПО ФАЙЛАМ СИСТЕМАТИЧЕСКИ НЕПОЛОН. Файл попадает в список, когда его увидели изменённым; увидели ровно те, что менялись в наблюдавшемся прогоне. Команда же пишет весь свой набор ВСЕГДА, и набор виден в её коде, а не в диффе одного случая.

КАК ДЕЛАТЬ. Выпиши команды жизненного цикла (task start, task log, task done, task move, task add) и по каждой спроси: какие файлы проекции она переписывает. Ответ читается в коде экспортёра, а не угадывается по git status. В #196 это дало бы обоих членов сразу и сняло бы одну задачу из двух.

ЗАМЕР ДЛЯ ГРАНИЦЫ ТОЖЕ ОБЯЗАТЕЛЕН: эпик в множество НЕ вошёл, и это проверено — за сессию из двух task start, task done, task add и task move git ни разу не показал проекцию эпика изменённой. Смежная память: [[инвентарь мест одного класса, составленный чтением, неполон]] (#461).
