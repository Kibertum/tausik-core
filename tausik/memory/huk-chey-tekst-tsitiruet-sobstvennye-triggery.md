Claude Code возвращает reason из {"decision":"block"} обратно в диалог как сообщение с ролью user. Если Stop-хук матчит регекспы по последнему пользовательскому сообщению, а его собственный reason цитирует триггерные фразы — хук срабатывает на себе на каждом следующем ходу. Проверено на живом транскрипте: _has_search_intent(SEARCH_RECOMMENDATION) = True, last_user начинался с 'Stop hook feedback:\n[TAUSIK rag-first nudge] ... (where is X / how does Z work / где определ)'. Гасил только stop_hook_active, то есть цена — лишний ход каждый раз.

Второй слой той же ловушки: транскрипт пишет ОДНУ запись на каждый content-блок, поэтому ход ассистента разложен на отдельные thinking / text / tool_use. Обход 'последнее сообщение по роли' отдавал первую же запись, часто tool_use, а _extract_text берёт только блоки text -> ''. Escape-hatch '"search_code" not in last_assistant' поэтому не снимался никогда: ВЫЗОВ инструмента не засчитывался, засчитывалось только слово в прозе.

Правила, выведенные отсюда:
1. Текст, который хук отдаёт наружу, не должен содержать своих же триггеров. Не цитируй примеры срабатывания в сообщении о срабатывании.
2. Всё машинно-порождённое (фидбек хуков, развёрнутые тела слэш-команд с <command-name>) фильтруй ДО матчинга.
3. Нудж про то, КАК агенту искать, — свойство пользовательского промпта. Ему место на UserPromptSubmit (additionalContext, ноль ходов), а не на Stop: Stop срабатывает уже ПОСЛЕ поиска и ничего не исправит, а блокировка Stop рендерится харнессом как ошибка хука и съедает вывод хода.
4. Проходя транскрипт назад за прозой, пропускай записи с пустым текстом.
