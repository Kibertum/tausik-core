Индекс, который ссылается на колонку, ДОБАВЛЕННУЮ МИГРАЦИЕЙ, нельзя положить ни в INDEXES_SQL, ни только в саму миграцию. Обе очевидные попытки ломаются, причём каждая — на своём типе базы.

INDEXES_SQL применяется в init_schema ДО миграций. На существующей базе колонки ещё нет: init_schema падает с «no such column» у КАЖДОГО обновляющегося пользователя, а свежие базы при этом зелёные. Поймано вживую в сессии #159 обычным вызовом CLI, ни один тест не заметил.

Только в миграции — тоже неверно, но наоборот: свежая база штампует текущую версию схемы и run_migrations не применяет НИЧЕГО, поэтому CREATE INDEX внутри миграции на свежей базе не исполняется никогда. Так молча разошлись шесть индексов до 1.8.

ПРАВИЛЬНЫЙ ДОМ — третий: POST_MIGRATION_INDEXES_SQL, применяемый ПОСЛЕ миграций на ОБОИХ путях, все операторы IF NOT EXISTS. Миграция сохраняет свой CREATE INDEX как исторический снимок; дублирование удерживается гейтом tests/test_schema_index_parity.py.

СМЕЖНОЕ ТОГО ЖЕ КЛАССА: перестройка таблицы (v43 для tasks) пересоздаёт индексы по списку, замороженному на момент написания миграции. idx_tasks_no_file_changes_declared из v41 ронялся перестройкой и не существовал ни на одной прошедшей v43 базе.
