РЕАЛЬНЫЙ СЛУЧАЙ (задача skill-activate-signature-bypass, сессия #117). В дерево скиллов писали ДВА пути: skill install (skill_manager.copy_skill) и skill activate (SkillsMixin.skill_activate). Проверка подписи стояла только на первом, фильтр копирования был написан как ЛОКАЛЬНАЯ функция _ignore внутри copy_skill. Итог: скилл, заблокированный install'ом, ставился одной командой activate — со всеми проверками в обход, вместе с hooks/ и .claude-plugin/, которые install вырезает. Через MCP activate доступен агенту напрямую и force не требует.

ПЕРВОПРИЧИНА — не забывчивость автора activate, а ТОПОЛОГИЯ: защита была физически недоступна второму потребителю, потому что жила внутри тела чужой функции. Пока проверка приватна для одного пути, второй путь не «забудет» её позвать — он НЕ СМОЖЕТ, и разойдутся они молча.

ПРАВИЛО: если у ресурса больше одного пути записи, инвариант выносится в общий модульный код и вызывается всеми путями. Проверять надо не «позвал ли автор», а grep-ом: список исключений / условие проверки обязан встречаться в исходниках ОДИН раз. Этот критерий проверяем механически и потому годится в блокирующие (см. km-promote-mechanical-checks-blocking).

КАК ИСКАТЬ ТАКОЕ ЕЩЁ: взять функцию-верификатор и посчитать её точки вызова. У check_skill_signature их было ровно ДВЕ во всём репозитории — одна в проде, одна в тестах. Верификатор с единственным прод-вызовом при нескольких путях записи — красный флаг.

СВЯЗАНО: конвенция #221 (гейт, не сумевший вычислиться, обязан блокировать) — в фиксе применена к нечитаемому запиненному ключу; конвенция #226 (неизвестно не равно пусто) — config_path=None даёт WARNING, а не молчаливый пропуск.
