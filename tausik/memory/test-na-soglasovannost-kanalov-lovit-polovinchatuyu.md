Случай из сессии #148, где приём доказал себя на практике в течение одной задачи.

Лимит сессии показывался из трёх мест: текстовая строка брала view["max_min"], компактный JSON — data["session_max_minutes"], а порог предупреждения шёл через effective_session_limit. Первые два были сырым значением из конфига, третий — эффективным. Починка: провести показ через ту же формулу.

Два view-словаря в status_view.py имели РАЗНЫЙ ОТСТУП (compact-ветка вложена глубже rich-ветки), поэтому правка одним движением с replace_all дошла только до одного. И вот ловушка: живой CLI после этого показал «/300m» — потому что текстовый рендер идёт как раз по починенной ветке. Ручная проверка подтвердила успех, которого не было: компактный канал, который читают /start и session_open, остался на 180.

Поймали тесты — и поймали ИМЕННО ПОТОМУ, что один из них утверждал `view["max_min"] == view["data"]["session_max_minutes"]`, то есть равенство каналов ДРУГ ДРУГУ. Тесты, проверявшие «каждый канал равен 300», тоже упали бы, но дали бы два независимых красных, из которых не видно, что дефект — рассогласование. А если бы автор написал только по одному тесту на канал и один из них забыл — половинчатость уехала бы в коммит.

ПРАВИЛО: когда чинишь расхождение N читателей одного факта, добавляй проверку «читатели равны друг другу» ПОМИМО проверок на конкретное значение. Первая ловит класс дефекта (рассогласование), вторые — конкретный экземпляр. И не считай ручной прогон одного канала подтверждением: он показывает ровно тот путь, по которому пошёл, а починка расхождения по определению касается нескольких путей.
