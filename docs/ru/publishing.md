# Две линии: где идёт разработка и что видит потребитель

<!-- doc-map: reader=maintainer; zone=reference -->

Решение #267 (29.08): **GitLab — линия разработки, GitHub — зеркало релизов.**
Оно заменило формулировку от 25.08 («GitHub становится основным местом
разработки»), которая пять сессий подряд не исполнялась: ветки жили в GitLab,
и решение приведено к практике, а не практика к решению.

Эта страница существует потому, что до неё процедура публикации жила ТОЛЬКО в
решениях. Решение, которое исполняется памятью агента, а не механизмом, не
исполняется — и пять сессий тому подтверждение.

EN mirror: [`../en/publishing.md`](../en/publishing.md).

## Кто есть кто

| Линия | Что это | Что там лежит |
|---|---|---|
| `origin` — GitLab | Линия разработки | Полная история: ветки, волны, вся бухгалтерия проекта. Сюда идёт каждый push, и по каждому push собирается CI (быстрая лента на стадии `test`, полная — на `test-full`). |
| `github` — GitHub | Зеркало релизов | Только выпуски, СПЛЮЩЕННЫМИ снимками. Замер #189: 16 коммитов против 405 у `origin/main`. Общей истории у линий нет — `git merge-base` пуст, корни разные. |
| `tausik/site` — GitLab | Сайт tausik.tech | Отдельный репозиторий (VitePress, сборка, nginx, CI сайта). В core и на публичной линии следов сайта НЕТ — замер смены #255 по обоим деревьям дал ноль, и `tests/test_site_lives_elsewhere.py` держит ноль (решение #368). Ссылка на tausik.tech в README — не след сайта, а указатель на него. |

Из этого следует одно практическое правило, которое стоит помнить дословно:
**`git push github v1-9-wave` — не синхронизация, а перенос 431 коммита
приватного архива в публичную линию.** Публикация есть акт над ДЕРЕВОМ, а не
над коммитом (решение #260).

## Порядок выкладки (решение #368)

GitLab хранит всю историю; в GitHub уезжает **только тег финальной версии** —
сплющенный снимок ОТФИЛЬТРОВАННОГО дерева, поставленный fast-forward-ребёнком
поверх подтверждённой публичной головы. «GitLab идентичен GitHub» означает:
содержимое снимка равно отфильтрованному дереву тега байт в байт, и это
равенство проверяет машина, а не память.

1. Релиз собирается и закрывается на линии разработки (GitLab); полный прогон
   зелёный по процедуре CI (`.gitlab-ci.yml`: клон, `bootstrap --no-detect
   --ide all`, `pytest -m ''`).
2. Снимок строится и проверяется кодом — `scripts/publication_snapshot.py`,
   команда `tausik publish`:

   ```bash
   # что войдёт, что останется, классы утечки на снимке; коммит не пишется
   tausik publish snapshot --from v1.9.0 --parent github/main --dry-run
   # снимок поверх публичной головы; печатает три проверки и команды выкладки
   tausik publish snapshot --from v1.9.0 --parent github/main
   # «идентичен»: дерево снимка == отфильтрованное дерево источника
   tausik publish verify --snapshot <sha> --from v1.9.0
   # после push анонимно проверить точный ref и всю достижимую историю
   tausik publish remote-audit --remote https://github.com/Kibertum/tausik-core.git \
     --ref refs/heads/main --from v1.9.0
   ```

   Команда работает над ОБЪЕКТАМИ: рабочее дерево, индекс, ветки и remote не
   трогаются. Отказ, если класс утечки на снимке не ноль, если `--parent` не
   коммит, если родитель имеет общую историю с линией разработки или исключённые
   пути в достижимой истории, либо если снимок не равен фильтру. Чего команда знать не может — так
   это вершину REMOTE: устаревший локальный `github/main` ловит fast-forward-only
   push на шаге 4, и ответ на тот отказ — fetch и снимок заново на новой
   вершине. Force не предусмотрен флагом — и запрещён файрволом.
3. Заявленная редакция SENAR опубликована: `tausik publish senar-check` спрашивает у GitHub Kibertum/SENAR тег редакции, которую заявляет TAUSIK. Код 1 — тега нет, код 2 — спросить не удалось; в обоих случаях выпуск TAUSIK не тегируется. Печатает обе версии и ссылку на релизы SENAR.
4. Владелец руками выполняет только push `main` после чтения вывода команды:
   `git push github <sha>:refs/heads/main` (только fast-forward). Тег пока не
   публикуется.
5. Запустить `Release qualification v2` с версией, точным коммитом разработки и
   точным коммитом публичного снимка. Непривилегированные lane jobs не имеют
   signing/release-environment секретов и не сохраняют Git credential; checkout
   получает только job token с `persist-credentials: false`. После успешных lint, полного Linux,
   macOS compatibility smoke, Linux upgrade-matrix и нативного Windows
   Cursor/Codex upgrade lane на точном снимке отдельный
   job в защищённом
   environment `release-qualification` берёт верификатор из неизменяемого SHA
   workflow, получает development object через защищённый read-only
   `DEVELOPMENT_REPOSITORY_URL`, независимо строит канонический candidate,
   отказывает, если `github.workflow_sha` не равен точному SHA публичного снимка, и
   проверяет, что Linux matrix JUnit содержит ровно 38 успешных тестов и
   покрывает все десять обязательных journey-сценариев, проверяет пустой Ruff JSON по trusted
   lint-конфигурации и удерживает Linux full-suite JUnit на пороге не менее
   14 444 collected, 14 291 passed и не более 167 skipped тестов. В 1.16 добавлены
   ровно четыре неприменимые к историческим заметкам проверки новых EN/RU страниц
   и два Windows-only теста байткода WSL. Прежние пропуски не изменились:
   сравнение выполнено с JUnit успешной квалификации 1.15. Затем он
   выпускает Ed25519-аттестацию для независимо доказанных lint, Linux full и
   изолированного upgrade-matrix lanes. Нативный Windows остаётся обязательным
   exact-SHA compatibility canary: аттестация связывает успешный GitHub job
   result `qualification-windows`, run ID, attempt, workflow SHA и candidate SHA,
   но не считает его доступный candidate-коду JUnit из 39 тестов доверенным
   evidence. Windows job всё равно валидирует диагностический JUnit через pinned
   harness, отключённый candidate `conftest.py` и bounded outer controller.
   macOS остаётся обязательной неподписанной зависимостью workflow.
   Для `DEVELOPMENT_REPOSITORY_URL` нужен GitLab deploy token только со scope
   `read_repository`. Нельзя выдавать `write_repository` или `api`; перед
   релизом проверяются identity авторитетного репозитория и права токена.
   Скачанные candidate и attestation положить в
   `dist/release-qualification-v2.json` и
   `dist/release-qualification-v2.attestation.json` и выполнить `tausik publish
   ci-check --snapshot <sha> --from v1.9.0 --tag
   v1.9.0`. Команда по-прежнему требует живой результат GitHub `Tests` для
   точного SHA и теперь однократно потребляет свежую совпадающую v2-аттестацию.
   Claim связывает версию, commit/tree разработки, commit/tree публичного
   снимка, подписанную ревизию верификатора, хэши проекций, доверенный ratchet
   сценариев и результаты всех
   обязательных lanes. Старый зелёный прогон, красный или отменённый lane,
   отсутствие прогона, таймаут, неопределённость API, отсутствующая или
   просроченная аттестация, несовпадение объектов, неверная подпись и повторное
   использование дают отказ без команды тега. GitLab CI нужен разработке, но
   не доказывает отфильтрованное публичное дерево.
   Аттестация истекает через 30 минут; после этого workflow запускается заново.
   Два пути в `dist/` используются по умолчанию. Флаги
   `--qualification-candidate` и `--qualification-attestation` указывают только
   на скачанные артефакты.
6. Только успешный `ci-check` печатает
   `git push github <sha>:refs/tags/v1.9.0` — **push по refspec**, а не
   второй `git tag -a`: имя `v1.9.0` уже стоит на релизном коммите линии
   разработки (из него шаг 2 и собирал снимок), и git откажется создать его
   второй раз. Одно имя, два объекта — релизный коммит на GitLab и снимок на
   GitHub — и одно отфильтрованное дерево, равенство которого доказал `publish
   verify`. `tests/test_publish_cli.py` выполняет напечатанные акты против
   голого remote и держит: `main` и тег на remote встают на снимок, а
   локальное имя остаётся на истории. Тег на GitHub — ЛЕГКОВЕСНЫЙ (ref без
   объекта тега и без сообщения; аннотированные теги до 1.8.0 ставились на
   orphan-линии руками); заметки к выпуску — это CHANGELOG и GitHub Release, а
   `published_tags.json` в любом случае записывает коммит. В том же заходе, на
   линии разработки, обновляется `tausik/published_tags.json` (см. «Теги»
   ниже).
7. Заметки к выпуску: тело GitHub Release лежит в `docs/release/body-<version>.md` (не в корне репозитория). Текст на английском; полный текст живёт в `docs/en/whats-new-X.Y.md` и `docs/ru/whats-new-X.Y.md`; тело ссылается на обе страницы. `tausik publish notes --version X.Y.Z --body-file docs/release/body-X.Y.Z.md` отказывает телу без любой из них; запускать до создания релиза и только после зелёного exact-SHA CI. Правило действует с 1.10; опубликованные теги ради него не перевыпускаются.
8. Авторство внешних вкладов сохраняется: чужие коммиты входят мержем или
   squash-ом с `Co-Authored-By` автора — иначе авторство стирается.

Начальная key ceremony выполнена: reviewed Ed25519 public key записан в
`PINNED_PUBLIC_KEY_HEX`, а соответствующий hex seed существует только как
repository secret `RELEASE_QUALIFICATION_SIGNING_SEED` (вместе с
`DEVELOPMENT_REPOSITORY_URL`). Неподготовленный или неверный ключ закрывает
шлюз. `publish ci-check` проверяет аттестацию по этому versioned public
identity и не получает приватный seed. Оба значения — lowercase hex ровно
32 байт (64 символа). Генерация и перенос выполняются на контролируемой
машине; seed нельзя печатать в CI-лог или shell transcript.

Одного provisioning недостаточно для активации официального пути. После push
reviewed workflow и public key в защищённую default branch первый защищённый
activation dry-run выполняется строго так. В момент dispatch точный SHA
публичного снимка всё ещё должен быть ревизией защищённой default branch,
которая поставляет workflow: verifier связывает `github.workflow_sha` и
отказывает, если он не равен публичному снимку. Если ветка продвинулась, нужно
построить и квалифицировать новый точный снимок, а не запускать устаревшее
доказательство.

1. Запустить workflow с этой ревизии и передать точные SHA development commit и
   public snapshot commit.
2. Подтвердить, что verifier получает авторитетный GitLab object через
   credential только со scope `read_repository` (без Approve GitHub
   environment).
3. Скачать оба артефакта: candidate и attestation.
4. Запустить `publish ci-check` как no-push acceptance check; не выполнять
   напечатанный refspec тега. Этот запуск расходует nonce, поэтому скачанные
   артефакты уже использованы. Для настоящего тега нужны новый workflow run и
   новые downloads.
5. Записать URL или ID workflow run и его доказательства в release task.
6. Только после этого объявить официальный qualification path активным.

Если activation завершилась ошибкой до создания release tag, публикация остаётся
замороженной, а её артефакты нельзя использовать повторно. Workflow и контракт
`ci-check` откатываются вместе, либо ошибка исправляется вперёд и весь exact-SHA
activation повторяется. После создания тега его не перемещают: выпускают patch
forward с новой версией. Любой credential, который мог раскрыться, ротируется.

Qualification v2 добавлен рядом с замороженным adherence v1 и не меняет его
manifest или verifier. Гарантия действует для официальной процедуры через
`publish ci-check`; локальный код не может отнять полномочия владельца
репозитория. Каждый nonce локально однократен за счёт атомарного маркера
`.tausik/release-qualification-v2-used/<nonce>`. Это не даёт cross-machine
защиту от replay, а удаление маркера стирает локальную память. Владелец может
удалить marker, выполнить сырой `git push`,
изменить workflow или ослабить настройки репозитория. Поэтому операционная
граница обязана дополнительно держать защищённую default branch, защищённый
environment `release-qualification` с узким секретом и approval, а также
server-side ruleset для тегов. Эти настройки GitHub внешние; перед каждым
официальным выпуском их нужно аудировать.

Linux matrix и full-suite запускают bootstrap, плагины и тесты candidate в
одноразовом непривилегированном контейнере без сети. Image, зависимости
контроллера, manifest сценариев и сценарный harness закреплены хэшами.
Предшествующий build-stage зависимостей одноразовый, но сетевой и writable; он
работает как root внутри Docker builder. У него нет секретов, host mounts или
Docker socket. В runtime переходят committed source кандидата, собранный каталог
зависимостей и offline wheelhouse. Runtime read-only, без capabilities, Docker socket и
доступа к host-каталогу артефактов. До исполнения внешний контроллер проверяет
фактический Docker inspect: точные user, network, rootfs, capabilities,
no-new-privileges, process limit, три ограниченных tmpfs и отсутствие mounts.
Runtime независимо сверяет соответствующие mount, status, interfaces и routes
Linux через `/proc`. После завершения pytest контейнер ждёт явный release signal.
Пока тот же контейнер работает, внешний контроллер через `docker exec` читает
не более 32 MiB недоверенного JUnit из 64 MiB tmpfs `/result`, валидирует его,
сам проверяет публичный remote и держит готовый lane JUnit только в памяти
контроллера. Затем он подаёт release signal, проверяет итоговый код завершения
контейнера, атомарно публикует host JUnit без перезаписи существующей цели и
удаляет контейнер и image.
Защищённый верификатор затем строит артефакты candidate и attestation. macOS compatibility smoke передаёт только
результат job через доверенную топологию `needs`. Для него нет отдельно
проверенной идентичности JUnit, и он исключён из подписанного claim
`REQUIRED_LANES`. Его bootstrap venv ставится offline из platform wheelhouse,
который скачан по тому же доверенному hash-lock до запуска candidate.

Эта граница не даёт обычному bootstrap, зависимостям, плагинам и тестовому коду
кандидата заменить доверенный контроллер или его evidence. Она не доказывает
честность намеренно вредоносного SUT, который распознаёт тест и имитирует
ожидаемый ответ. Для такой угрозы нужен независимый oracle или более сильная
модель исполнения; она не входит в claim этой release qualification.
После того как сам ledger-каталог стал устойчивым, на POSIX marker-файл и этот
каталог проходят `fsync`. Первое создание ledger-каталога всё ещё зависит от
поведения родительской файловой системы при потере питания. На Windows
эксклюзивное создание исключает конкурентный повтор, но power-loss durability
по-прежнему зависит от файловой системы и внешних server controls выше.

## Containment, если публичный ref загрязнён

Чистая вершина не исправляет раскрытого предка. Если `publish remote-audit`
показывает неверное дерево, исключённый путь в истории или общую историю с
разработкой, публикация останавливается:

1. Записать точные анонимные значения `ls-remote` всех затронутых веток и тегов.
   Манифест и bundle хранить только в контролируемом владельцем месте, не в
   публичном репозитории.
2. Проверить достижимое содержимое на credentials и персональные данные, не
   копируя найденные литералы в отчёт. Подтверждённый credential сначала
   ротируется. Решение об уведомлении по персональным данным принимает владелец.
3. Построить независимый от истории кандидат командой `tausik publish recovery
   --from <development-release-ref>`. Она создаёт orphan commit-object, не двигает
   refs и намеренно не печатает push-команду. `publish verify` обязан подтвердить
   равное отфильтрованное дерево и отсутствие исключённой достижимой истории.
4. До мутации назвать точные старый SHA, новый SHA и каждый затронутый ref;
   сохранить старые объекты приватно. Перезапись `main` ломает обычный pull,
   удаление ветки убирает ссылки, перенос или удаление тега меняет либо ломает
   чужие pins.
5. Force-with-lease, удаление ветки, перенос или удаление тега, правка Release,
   запрос на удаление cached objects и публичное уведомление требуют отдельного
   явного разрешения владельца на эти точные действия. Разрешение обычного
   релиза не является разрешением containment.
6. После разрешённой мутации выполнить `publish remote-audit` через анонимный URL
   для каждого оставшегося точного ref. Missing, network или fetch error — отказ,
   не green. Ни один рекламируемый ref не должен достигать загрязнённых коммитов.
7. Rollback восстанавливает старые refs и тем самым снова раскрывает данные. Он
   допустим только по новому явному решению владельца.

Обычная публикация остаётся fast-forward-only. Recovery применяется только к
измеренному инциденту и не включается проектным конфигом.

## Что публикуется: фильтр, а не всё дерево

До #368 наружу уходило ВСЁ отслеживаемое дерево, включая `tausik/` — папку
собственной бухгалтерии проекта: замер смены #251 дал на `github/main` 2438
файлов `tausik/` из 3576, то есть 70 % того, что клонировал потребитель, — и
именно в этой бухгалтерии жили объявленные ниже классы утечки.

Теперь исключения — ОДНА объявленная константа
`publication_snapshot.EXCLUDED_FROM_PUBLIC_SNAPSHOT`, удерживаемая
`tests/test_publication_snapshot.py`:

| Остаётся на линии разработки | Почему |
|---|---|
| `tausik/tasks/`, `tausik/stories/`, `tausik/epics/`, `tausik/decisions/`, `tausik/memory/`, `tausik/graph-snapshots/` | проекция состояния для переноса между машинами по ветке; потребителю фреймворка не нужна |
| `docs/ru/research/release-111-economy-plan-2026-10-01.md` | внутренний план выпуска со ссылками на трекер разработки; публичные результаты остаются в других документах |
| `.gitlab-ci.yml` | пайплайн линии разработки |
| `scripts/ci_lane_dev.py`, `tests/test_ci_lane_dev.py` | чтение того пайплайна: инструмент для хоста, с которым у публичного репозитория нет отношений. `cli_push_ok` импортирует модуль НЕОБЯЗАТЕЛЬНО, поэтому опубликованное дерево работает без него и молчит, а не жалуется |

`AGENTS.md` и `CLAUDE.md` остаются публичными, но snapshot очищает их порождённые
блоки `DYNAMIC`. Стабильные правила агента публикуются; текущая сессия разработки,
имена задач и путь к журналу хоста — нет.

Храповики `tausik/*.json` (`gates`, `policy`, `published_tags`,
`spec_coverage`) **едут**: их читают гейты и тесты. Замер на дереве 1.9:
1308 файлов уходит, 3090 остаётся.

Классы утечки проверяются машиной по-прежнему — на ВСЁМ дереве
(`tests/test_publication_lines.py`) и на СНИМКЕ (`tausik publish snapshot`
отказывает при ненулевом классе). Замер смены #256:

| Класс | Было (#180) | Всё дерево | Снимок | Статус |
|---|---|---|---|---|
| Локальный путь с именем пользователя | 12 файлов | **0** | **0** | вычищено, удерживается храповиком |
| Имена чужих проектов | 44 файла | **0** | **0** | вычищено, удерживается храповиком |
| Внутренний хост `gitlab.yumash.ru` | 17 файлов | 4 файла | **0** | остаток объявлен на дереве, на снимке ноль |
| Путь среды разработки вида `D:\Work` | не измерялся | 22 файла | **0** | остаток объявлен на дереве, на снимке ноль |

Остаток на всём дереве живёт в бухгалтерии, которая наружу не едет; его
число зафиксировано, рост краснеет. На снимке оба класса — ноль, и это не
объявление, а отказ команды.

Файл, который ОПИСЫВАЕТ утечку — эта страница, задача о ней, решение, сам
тест, — утечкой не является. Иначе проверка запретила бы писать о проблеме,
что дороже самой проблемы.

## Теги: публичный тег — обещание, а не закладка

README велит подключать репозиторий сабмодулем, а сабмодуль пинится SHA или
тегом. Значит перемещение опубликованного тега переставляет ЧУЖОЙ пин на другое
дерево, и молча. Тем же доводом здесь уже запрещён force-push, и сам git
отказывается перетирать тег словами «would clobber existing tag». Поэтому:

**опубликованный тег не двигается никогда, не удаляется и не перевыпускается.**

### Что измерено (смена #233, `git ls-remote` обоих линий)

| | публичная (github) | приватная (origin) | локально |
|---|---|---|---|
| тегов | 9 | 17 | 22 |

Только у origin: `v1.1.0` `v1.2.0` `v1.3.0` `v1.3.2` `v1.3.7` `v1.4.0` `v1.4.1`
`v1.4.2` `v1.5.2`. Только у github: `v1.5.3`.

Общих имён восемь, и **все восемь указывают на РАЗНЫЕ объекты** — совпадающих
нет ни одного:

| тег | github | origin |
|---|---|---|
| `v1.5.5` | `8084cc9f` | `c61bbb10` |
| `v1.5.6` | `f380a2e0` | `698f2d00` |
| `v1.5.7` | `7c311e81` | `7eb40153` |
| `v1.5.8` | `49dcf47d` | `e4f961b0` |
| `v1.6.0` | `c50c6de9` | `af283bdf` |
| `v1.6.1` | `e036321d` | `cdde825a` |
| `v1.7.0` | `bf13a09e` | `2ec833a5` |
| `v1.8.0` | `623fb4ee` | `3866702f` |

Причина измерена, а не предположена: публичные теги ставились на orphan-снимке,
у которого нет общего предка с настоящей историей. Один и тот же номер релиза
называет два разных дерева — и до 1.9 имя тега НЕ является общим адресом между
линиями.

### Что с этим делается

Прошлое не чинится: тринадцать недостающих тегов задним числом НЕ выставляются,
восемь разошедшихся НЕ приводятся друг к другу. Любое из этих действий
переставило бы чужой пин.

Расхождение объявлено этой таблицей и удерживается механизмом:
`tausik/published_tags.json` хранит девять пар «имя → объект», снятых с
публичной линии, а `tests/test_published_tags_are_promises.py` сверяет с ними
живой `ls-remote`. Изменение, исчезновение И появление считаются движением.
Недоступная сеть даёт ПРОПУСК с объяснением, а не зелёное: проверка, которая
проходит, не дозвонившись, утверждает то, чего не измеряла.

### Шаг выкладки, добавленный с 1.9

С 1.9 два объекта за одним именем — это МОДЕЛЬ, а не случайность (решение
#368): имя на линии разработки стоит на релизном коммите с его историей, имя
на GitHub — на снимке отфильтрованного дерева этого коммита, и деревья равны
под фильтром по `publish verify`. Что в восьми строках выше было необъяснённым
расхождением, с `v1.9.0` — заявленное отношение. `tausik/published_tags.json`
обновляется на линии разработки **в том же заходе, что и push**, коммитом
сразу после него: снимок не может нести собственный sha, поэтому копия этого
файла внутри снимка по построению отстаёт на один релиз — у клона потребителя
нет remote с именем `github`, и проверка обещания там ПРОПУСКАЕТ с объяснением,
а не утверждает сравнение, которого не делала.
